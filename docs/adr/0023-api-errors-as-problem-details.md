# The API answers with bare resources and RFC 9457 errors

The HTTP API is used directly from any language, not only through the TypeScript client and the CLI, so its responses follow standards rather than oRPC's own format. A successful response is the resource itself, without an envelope, as Stripe, GitHub, OpenAI, Anthropic, Google's API design rules (AIP-131) answer; Cloudflare Workflows' binding returns bare objects too. An error is an RFC 9457 Problem Details document, `application/problem+json`, with `type: "about:blank"`: the HTTP status carries the meaning, and `title` and `detail` are for people. No problem gets a `type` URI or a code of its own, even where two share a status: callers act on the status, as with any HTTP API, so the hub not being set up is a 503 as a proxy's is. Inside the hub and the TypeScript client, errors keep oRPC's codes, one per status, so code still branches on `UNAUTHORIZED` or `NOT_FOUND`.

oRPC supports this through its own options and plugins. The handler encodes errors as Problem Details, and the OpenAPI generator describes them with the Problem Details schema; both give the media type, which the link reads as JSON, and the link decodes the documents back into oRPC's errors. oRPC's response validation plugin marks errors the contract declares for a call as typed, as oRPC's handler does. That leaves what does not come from the hub to the link's own `fetch` option: an error response not labelled `application/problem+json`, such as a proxy's page while the hub restarts, would fail to parse as JSON, so the link reads it as the `about:blank` problem of its status, titled with the status's reason phrase, as RFC 9457 has it. The shared link lives in the contract package, so every TypeScript client gets it from one place. The hub builds every document with hono-problem-details: oRPC's errors through the encoder, and errors outside oRPC through the library's error handler, so both use the same titles (RFC 9110's reason phrases) and the same media type, `application/problem+json; charset=utf-8`. The link takes its phrases from jshttp's `statuses`, whose table Node's `http.STATUS_CODES` matches, and which loads in a browser too, where the dashboard runs the link; that table still names 413 and 422 by their phrases before RFC 9110, and a status it lacks, such as Cloudflare's 52x, is titled with its number.

`detail` tells a caller what the contract makes public. Its words are for people and may change. The HTTP status carries the meaning. Invalid input lists its problems, as oRPC's validation recipe does; an error the contract declares for the call shows its own message; any other error answers with its title alone, so the hub's internals, such as its own output failing its schema, stay private.

A caller can correct one field or one job in a group using the optional `errors` array. When the failing stage locates any issue, it includes every issue it found. Each entry has a human-readable `detail`. An entry with a location has one string naming it. A `pointer` is a plain RFC 6901 pointer into the JSON body. The empty string names the whole body, and a pointer may name a required member the caller omitted. A `parameter` names an OpenAPI query or path parameter. A `header` names a request header. These names come from [JSON:API's error source](https://jsonapi.org/format/#error-objects). OpenAPI treats both path and query values as parameters. The top-level detail still gives the complete explanation.

The hub uses this extension on `about:blank`. RFC 9457 defines extensions in terms of a problem type. Here the HTTP status already gives callers their next action, and a separate type URI would add an identifier to maintain solely to locate a field. Better Auth refusals carry the library's message. We state a library limit in the contract when its measurement and bounds match exactly.

The Runner protocol is not part of the API: both ends are ours. The hub's refusals of a Runner before its socket opens, as unknown (401) or for offering no protocol version it supports (400, ADR 0026), are Problem Details too, each with a `code`, so a Runner reads every refusal one way.

## Considered options

- oRPC's own error format, `{ defined, code, message, data }`: no other API uses it, `defined` describes oRPC's internals, and it changes with oRPC's major versions (version 2 dropped `status`), which would break callers' generated clients.
- Cloudflare's v4 envelope, `{ success, result, errors, messages }`: the minority among comparable APIs, and Cloudflare's own Workflows binding does not use it.
- An `{ error: { code, message } }` body, as Stripe, OpenAI and Azure answer: the most common shape, but each API defines its own fields, so ours would be a format of our own.
- A `code` member or a `type` URI for each error: a second identifier beside the status, or URIs to keep stable, for errors that the status already tells apart. Zod's per-issue codes also change across major versions. An entry can gain a code when a program needs to branch on the kind of issue.
- Problem Details sent as `application/json`: less code, but tools identify Problem Details by its media type.
- Leaving locations in `detail` requires clients to parse a validation library's printed layout.
- A pointer plus an `in` discriminator departs from JSON:API's familiar names. Headers and path parameters have names of their own outside the JSON document.
- A pointer into a synthetic object with `params`, `query`, `headers` and `body` avoids consulting the route. Clients would have to construct that object before resolving a body pointer.
- hono-problem-details' Zod adapter joins fields with dots in its `{ field, message, code }` shape. Label keys can contain punctuation, so callers need escaped, unambiguous tokens.
- Arrays of path segments, as in Zod and FastAPI, lack a standard wire representation. Zod's flattened and tree-shaped errors would also couple the API to a library format.
- A separate validation call costs another round trip. Its answer about a custom ID or a Blob could already be stale at submission.
- RFC 9457's example uses the URI fragment form of JSON Pointer, which requires percent encoding. JSON:API and pointer libraries take plain pointers.
- Translating Better Auth error codes to fields would silently lose locations when the library renamed a code.

## Consequences

Paths outside the API answer 404 as Problem Details too, and so do failures outside oRPC, such as a hub missing its settings; unexpected errors are logged and answer 500 with a generic `detail`. Better Auth's own routes under `/api/auth` keep Better Auth's error format. When the hub publishes its OpenAPI document, the error responses there are described as Problem Details.
