# A Usage record keeps its use by model and by tool

A job's Usage record says what the job used since its previous end, in tokens and US dollars. What that use went to, by model and by tool, lives only on the job's progress, as pi's running totals per model (`provider/modelId`) and per tool, and it goes when the job is deleted. A split not recorded at an end can never be recovered, so each record keeps its own: `usageRecord.usage`, `{ "models": { "<name>": entry }, "tools": { "<name>": entry } }`, both maps always present. The job's row keeps, in `recordedUsage`, a copy of its usage at its last end, beside `recordedTotalTokens` and `recordedCostUsd`, and set by the same statement under the same conditions. Nothing reads the split yet.

An entry holds the additive counters of pi's `Usage`, under pi's names: `totalTokens`, `input`, `output`, `cacheRead`, `cacheWrite`, `cacheWrite1h` and `reasoning`, and `cost` with `total`, `input`, `output`, `cacheRead` and `cacheWrite`, each the difference between the job's usage at this end and at its previous one. pi reports `cacheWrite1h` and `reasoning` only where the provider gives such a figure, and the others for every name. A counter absent at this end from a name present then is not 0, so it stays absent from the entry; a name absent at one end counts as 0 there. A counter that is not a number, as a snapshot stored before the protocol checked the counters may hold, counts as absent, so it cannot fail the statement that ends the job. `cost.totalFromProvider` is left out, as pi never updates it on a running total. A name whose counters did not change since the previous end gets no entry, and an end with no use still gets its record, with empty maps.

The totals are the sums of the job's usage, so the split is taken from the same snapshot of the job's usage that the totals are taken from, less the job's row as the ending statement found it, and the subtraction runs in SQL as `numeric`, as the totals' does. jsonb numbers are `numeric`, so nothing rounds. For every end whose previous end was recorded with the split, the record's entries therefore add up exactly to its own `totalTokens` and `costUsd`: both are required in an entry, so a counter left absent does not affect that sum. A name whose counter shrank gets a negative entry rather than none: pi's totals per name only grow, so a shrinking one would be pi's fault, and leaving it out, or clamping it at 0, would break the sum. The Runner protocol checks each counter the hub subtracts as a number, token counts as integers, so a Runner's malformed counter is refused with its report.

Use a Runner reports after an end is counted, like the totals, by the job's next end if it is resumed, and not at all if it is deleted first.

The record's `usage` is not null and has no default, so an end written by a previous release of the hub, which gives no split, fails: its record and the job's recorded totals are written by one statement or transaction, so neither a record without a split nor a totals baseline moved without `recordedUsage` is kept. Records written before the column have empty maps. A job's `recordedUsage` starts empty where its records have counted nothing, which is exact, as for a job that has not ended. Where they have counted something, its usage at its last end was never kept, and it starts as its progress's usage: exact where the job has used nothing since its last end, and otherwise short by what it used between that end and the migration. The job's first end after the migration then has entries that fall short of the record's totals by as much, never over, the difference reading as use not attributed to any model or tool. Nothing is counted twice.

## Considered options

- A child table, one row per record and name, with typed columns: each end would insert into two tables, and the split would be kept apart from its record. A `jsonb` column goes with its record wherever the record goes, and one insert keeps its shape. Every report filters on the record, by day, status, labels, Batch, submitter or Runner, so `jsonb_each` over the records already read replaces a join.
- Clamping a shrinking counter at 0, or refusing the report that shrinks it: either breaks the sum of a record's entries, and the shrink, if it ever happened, would be pi's to fix.
- Only tokens and cost per name: the counters per kind of token, and their costs, would be lost for the jobs run before they were recorded, as the split itself would be.

## Consequences

Each end's statement takes `jsonb_each` of the job's usage and of its `recordedUsage`, matched by name, for each of the two maps. A record's `usage` holds names only for what the job used since its previous end, so its size follows the models and tools of one run.

## When to reconsider

Move the split to a child table with typed columns and an index on the name when reads by model or by tool become slow at real volume. Add a monthly rollup by model and by tool if Usage records come to be deleted after a retention period and those totals are needed beyond it. If usage comes to be dated by when the work happened, as ADR 0044's reconsideration describes, a record per end no longer fits: record each increment in a ledger instead.
