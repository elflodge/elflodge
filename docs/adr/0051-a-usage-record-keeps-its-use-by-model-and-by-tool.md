# A Usage record keeps its use by model and by tool

A job's Usage record says what the job used since its previous end, in tokens and US dollars. What that use went to, by model and by tool, lives only on the job's progress, as pi's running totals per model (`provider/modelId`) and per tool, and it goes when the job is deleted. A split not recorded at an end can never be recovered, so each record keeps its own: `usageRecord.usage`, `{ "models": { "<name>": entry }, "tools": { "<name>": entry } }`, both maps always present. The job's row keeps, in `recordedUsage`, a copy of its usage at its last end, beside `recordedTotalTokens` and `recordedCostUsd`, and set by the same statement under the same conditions. Nothing reads the split yet.

An entry holds every additive counter of pi's `Usage` that the job's usage reports, under pi's names: `totalTokens`, `input`, `output`, `cacheRead`, `cacheWrite`, and `cost` with `total`, `input`, `output`, `cacheRead` and `cacheWrite`, each the difference between the job's usage at this end and at its previous one. pi reports all of them but `cacheWrite1h` and `reasoning` for every name, and those two only where the provider gives such a figure. A counter absent at both ends is not 0, so it stays absent. `cost.totalFromProvider` is left out, as pi never updates it on a running total. A name whose counters did not change since the previous end gets no entry, and an end with no use still gets its record, with empty maps.

A record's entries add up exactly to its own `totalTokens` and `costUsd`. The totals are the sums of the job's usage, so the split is taken from the same snapshot of the job's usage that the totals are taken from, less the job's row as the ending statement found it, and the subtraction runs in SQL, on token counts as `bigint` and dollars as `numeric`, as the totals do. jsonb numbers are `numeric`, so nothing rounds. A name whose counter shrank gets a negative entry rather than none: pi's totals per name only grow, so a shrinking one would be pi's fault, and leaving it out, or clamping it at 0, would break the sum. The Runner protocol checks each counter the hub subtracts as the number SQL casts it to, so a Runner's non-numeric counter is refused with its report instead of failing the statement that ends the job.

The record's `usage` is not null and has no default, so an end written by a previous release of the hub, which gives no split, fails: its record and the job's recorded totals are written by one statement or transaction, so neither a record without a split nor a totals baseline moved without `recordedUsage` is kept. Records written before the column have empty maps. A job's `recordedUsage` starts as its progress's usage where its recorded totals equal its progress totals, as then it has used nothing since its last end; elsewhere its usage at its last end was never kept, and it starts empty. That is exact while the job's records have counted nothing, as for a job that has not ended. A job that used more after an end that counted something counts that earlier use again in its next record's entries, which then exceed the record's totals by the job's recorded totals.

## Considered options

- A child table, one row per record and name, with typed columns: an insert that writes a record would write its rows too, from the same rows the record is built from, and a deleted job's records would have to keep theirs; should records be partitioned by month (ADR 0044), the child rows would need their own partitions. A `jsonb` column goes with its record, and one insert keeps its shape. Every report filters on the record, by day, status, labels, Batch, submitter or Runner, so `jsonb_each` over the records already read replaces a join.
- Clamping a shrinking counter at 0, or refusing the report that shrinks it: either breaks the sum of a record's entries, and the shrink, if it ever happened, would be pi's to fix.
- Only tokens and cost per name: the counters per kind of token, and their costs, would be lost for the jobs run before they were recorded, as the split itself would be.

## Consequences

Each end's statement takes `jsonb_each` of the job's usage and of its `recordedUsage`, matched by name, for each of the two maps. A record's `usage` holds names only for what the job used since its previous end, so its size follows the models and tools of one run.

## When to reconsider

Move the split to a child table with typed columns and an index on the name when reads by model or by tool become slow at real volume. Add a monthly rollup by model and by tool if those totals are needed beyond the records' retention. If usage comes to be dated by when the work happened, as ADR 0044's reconsideration describes, a record per end no longer fits: record each increment in a ledger instead.
