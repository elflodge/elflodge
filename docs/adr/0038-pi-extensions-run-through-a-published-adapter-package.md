# Pi extensions run through a published adapter package

Pi coding-agent extensions run on pi-durable through `@elflodge/pi-durable-extension-adapter`, a package of its own in this workspace, published with the same version as the rest (ADR 0032). It imports nothing of Elflodge, so any pi-durable host can use it; pi-durable has no way to run coding-agent extensions itself (earendil-works/pi#10386).

A host prepares the extensions once: Pi's own package manager installs them, as `pi install` does, and Rolldown bundles them with the package's runtime into one build, treating Pi's packages as free of side effects so only the parts in use remain, except three modules whose import registers pi-ai's image providers and sets the default stream function of Pi's `Agent`, found by listing every import-time statement in Pi's modules. The entry of each extension installed in the host's directory is written beside its source, so the files a package reads relative to it (its `package.json`, templates, WebAssembly) are found; extensions from local paths elsewhere and shared chunks go in a directory of their own, with TypeBox in a chunk of its own, which breaks a cycle of top-level awaits one extension otherwise deadlocks on. Native add-ons stay where they are installed, and the host loads each in its main thread before starting workers: Node unloads a worker's add-ons when it exits, and one with a thread-local destructor left behind then crashes the process (zhangyuang/node-ffi-rs#145); one the process holds is never unloaded. Photon, Pi's image library, which reads its WebAssembly beside its module, also stays installed. The build runs in a child process: in a worker thread, Rolldown's native runtime, its threads and their memory stay in the host process after the build, about 775 MiB unused. The bundle resolves Pi's packages as Pi's loader does for extensions, from the package's own copy of the coding agent, with pi-ai's root as Pi's extension view of it and Pi's former package names. Extensions run in a few worker threads shared by all conversations, with one instance of each extension per conversation. A conversation's instance is created when the host attaches it. The host installs a pi-durable extension for each attached conversation, `pi-durable-extension-adapter:<conversation ID>`, with that conversation's tools and only the hooks its extensions listen to, and adds it to the conversation's stored `extensions` selection, keeping the rest of it, so each conversation is offered only its own extensions' tools, as described by them, as a Pi session is; tools can differ between conversations, such as an MCP server's. pi-durable selects every installed extension when the host sets no default selection, and lets a later tool replace one of the same name, so the host must set `settings.extensions`, and `attach` fails when it finds the default selection selecting one: a conversation's extension selected without the stored selection naming it, by the attaching conversation or, when that one stores an exact list, by an attached one that edits the default. A conversation created from an attached one inherits its selection; attaching it replaces the inherited name with its own, and otherwise its calls to the tools fail. An install or uninstall costs pi-durable under 0.1 ms with a thousand extensions installed, once per attach, close or registration; a request resolves only the defaults and the conversation's own. Hooks and tools know only their conversation's ID, which is unique within one Harness, so a registry serves one Harness.

In the worker, Pi's own loader builds the `pi` object each extension's factory receives (`loadExtensionFromFactory`, which Pi's root does not export), reached by its file path in the package's own copy of the coding agent, with `PI_PACKAGE_DIR`, Pi's documented override, defined in the bundle as that copy's directory, since Pi otherwise looks for its own files beside its code, which the bundle moves, with `exec` replaced to run in the host's environment and `on` wrapped to tell the host of a subscription made after loading. Pi's root reaches its loader only through `DefaultResourceLoader`, whose every load scans the working directory, its ancestors and the user's home for skills and settings, and which adds about 18 to 21 MiB per worker, measured twice. It dispatches events through Pi's exported `ExtensionRunner`, so handler order, how results combine and how a failing handler is isolated are Pi's own, and follow Pi's releases. The runner takes Pi's `SessionManager` and `ModelRegistry` classes, which it only hands to extensions as `ctx.sessionManager` and `ctx.modelRegistry`; the package passes objects with the methods extensions use, over the host's journal and models, with one type assertion each. Reads of the history and the agent are synchronous in Pi, so the worker waits for the host's answer (`sync-message-port`); the host never waits for a worker, and pi-durable runs hooks off its Session line, so a handler can read the history too. Writes such as `appendEntry` travel on the same channel and the host carries them out before a later read, so an extension reads what it just wrote, as in Pi. pi-durable runs a tool's `prepareArguments` synchronously on the host, so for a tool that has one the host parses arrays and objects sent as JSON text, and the worker runs the tool's own before executing.

The host runs Pi's lifecycle events from pi-durable's hooks, installing only those some attached conversation listens to. pi-durable has no hook where a run starts, so a run's first request stands for it: it runs `before_agent_start` and `agent_start` once, describing the run by the oldest of the inputs pi-durable placed for it (`LiveRun.inputs`, each read through its submission), and not for a continuation after an answer or a `continue` after a failure, and records what they return as a memo of the generation task, so a retry or a crash sends the same additions without running them again. What handlers add to the system prompt goes into each of the run's requests as sections of its system message, laid out by the package as Pi lays out those parts, since Pi's own function builds its whole prompt with its default rules among the guidelines, and kept in a conversation document of the package's, by the run's first entry, for the run's later rounds, generation tasks of their own that a host restarted mid-run also sends; the messages they return go with the first request and are written to the conversation, where they land after its answer; a tool selection they change, or `setActiveTools`, configures the conversation's model tools, which a request fixes before its hooks run, so it applies from the next request. A returned `systemPrompt` is ignored, since pi-durable builds the prompt. `turn_start`, `message_end`, `turn_end`, `agent_end`, `agent_settled` and the tool execution events are observed from the generation and tool hooks, their results ignored, except `tool_execution_update`, which the worker emits with each partial result an extension's tool reports and whose handlers the tool's result waits for, as in Pi's agent loop; `agent_end` follows only runs that answered, as `afterRun` does, and `agent_settled` right after it, while the run still holds the conversation busy, since pi-durable gives no later moment an extension can rely on: its observers neither wait for handlers nor replay what a crash cut off. `submission.wait()` resolves before `afterRun`, so `close` waits for that run's end to reach the extensions. `session_before_compact` maps to `beforeCompact`: a cancel declines, a custom summary replaces pi-durable's. Extensions that register model providers are not supported: the host makes model calls with its own models, and a provider an extension defines would have to run on the host. Tools' prompt snippets and guidelines depend only on the tools a request offers, so they are a pi-durable prompt section, laid out as Pi lists its active tools'.

When a worker exits, for instance out of memory under the host's `resourceLimits`, the calls in flight fail with the reason, and the host opens its conversations' extensions once more on another worker, with `session_start` reason `resume`, as after a restart; their hooks and tool calls wait while they load. Without that, the conversation goes on without its extensions, and every host would write the same close and attach again; the caller still decides about the job, through `onLost` on each attachment, since conversation IDs repeat across Harnesses, or `onWorkerExit` on the host, and can turn reopening off. A reopen that fails, as when the new worker also exits while loading or an extension that loaded before fails to load, leaves the conversation lost rather than try again, which ends a loop of crashes at load; until a reopen succeeds, the conversation keeps what its extensions registered before, so a `tool_call` gate still blocks. A lost conversation's extension tools fail and its hooks do nothing, except that one whose extensions handle `tool_call` has its tool calls blocked, as Pi blocks a call when a `tool_call` handler fails: the package cannot tell a gate from an observer.

Measured with `pi-web-search` and `pi-web-access`, PSS per worker on Node 26: about 99 MiB loaded as shipped, 24 bundled, and 35 to 39 in a host, with the runtime, Pi's runner and a conversation.

## Considered options

- Extensions in the host's own thread: their synchronous work would stall pi-durable and every conversation (`pi-web-access` parsing a 1.05 MB page blocked its thread for about half a second), and an uncaught error, a `process.exit()` or a full heap would end the host; `resourceLimits` exists only for workers.
- A process per conversation, or extensions loaded as shipped: about 99 MiB per instance or worker, for a Runner that hosts hundreds of conversations.
- Building the `pi` object with code of our own, filling Pi's exported `Extension` record as its loader does: about 300 lines that repeat Pi's loader and drift from it with each release. Reaching the loader by path instead pins it to the package's own copy of Pi, so a release that moves the file fails the type check and the build rather than drifting.
- Pi's loader through `DefaultResourceLoader`'s `extensionFactories`: the disk scans and the memory above.
- One pi-durable extension shared by a registry's conversations, which needs no default selection from the host: each conversation is offered every attached conversation's tools, described by the first to register each name, so one conversation's tool names and descriptions reach another's prompt and its calls to them fail.
- Filtering each conversation's tools with pi-durable's `tools` or `modelTools` setting over a shared extension: a filter that removes others' tools writes to every other conversation for each new name, one that lists the conversation's tools must list the app's too and stops following its defaults, and one name with two descriptions cannot be told apart.
- One bundle directory for all entries: an extension that reads a file next to its code, or its own `package.json`, does not find it.
- Describing the run by the entries it started with: entry kinds and order mistake a compaction's summary or a message written meanwhile for the prompt, and cannot tell which of several inputs started the run.
- Running `before_agent_start` when the host submits input: it misses runs that queued input, an extension's message or a continuation starts.
- Prompt additions as a pi-durable prompt section: sections render before the request's hooks run and cannot carry messages.
- A run's prompt additions kept in memory, or in a hidden entry: memory is lost when the host restarts mid-run, and an entry adds to the conversation's history with every run, where a document holds the latest additions, as pi-durable keeps an extension's own state.
- Building in a worker thread: at 100 conversations the process held 867 MiB, against 230 with the build in a child process; a child takes about 50 MiB more than a worker thread while it runs.
- Caching the bundle between starts: a key that misses a change, such as an upgrade of this package or an edited local extension, runs an old build, to save about a second at start.
- Dispatching events with code of our own: about 400 lines that repeat Pi's runner and drift from it with each release.
- A real `ModelRegistry` in each worker: it needs Pi's `ModelRuntime`, which loads every built-in provider, about 29 MiB more per worker.
- A synchronous call from the host to the worker for `prepareArguments`: a host waiting on a busy worker would stall every conversation.
- Effect's RPC and worker modules for the calls between host and workers: they would load Effect into every worker, which loads only the extensions and the parts of Pi they use, for what birpc does in 7 KB.
- Effect's `Pool` for the workers: it caps how many borrowers an item takes and makes the rest wait, while a conversation keeps its worker for as long as it runs.
- A worker pool library (Piscina, Tinypool, poolifier, workerpool, jest-worker and others): they schedule tasks, so a conversation that holds its worker between calls is invisible to their idle tracking and shutdown, and those that replace a worker that exited (Piscina, poolifier) restore capacity, not the conversations it hosted; the conversation map, placement and reopening would still be ours.
- Only reporting a worker's exit: the model cannot restart a worker, so it would lose the extensions' tools, and with a `tool_call` handler every tool, for the rest of the conversation, while reopening fails only the call in flight and leaves the model to decide whether to call it again.

## Consequences

The package uses no Effect today. Its runtime checks are TypeBox schemas: Pi already installs TypeBox, at the version the package pins, while Effect would add 61 MB to every install for a few small schemas, and in the workers about 1 MiB each, even for `Equal` alone. It would take Effect only for a feature shown to be much simpler to write with it. Extensions run with the host process's permissions; a worker thread is not a sandbox. Bundled code reads files relative to the file it is bundled into, so code that moves to the bundle's directory finds none of its package's files. Extensions that start Pi as a process of their own, such as `pi-subagents`, are not supported. Module-level state is shared by the conversations on a worker. An extension that does not bundle is not loaded. A tool's own `prepareArguments` runs after pi-durable has validated the arguments. The package pins the coding agent's exact version, since it relies on internal files any release may move or change (its loader, its extension view of pi-ai, the modules whose import registers providers), and an application installing a range would take a release no test ran on, before the package's own tests could catch it; so each Pi release needs a tested release of the package, which also rechecks the coding agent's dependencies left installed, such as Photon, and prepare fails, naming the file, if an override installs a copy without one of those files. pi-durable, pi-ai and chord are peers on their public APIs and keep a caret range, so an application on a newer Pi than the package's installs a second pi-ai, for the worker. When pi-durable can run coding-agent extensions itself, the package's README points to it.

Reconsider reaching Pi's loader by path when Pi's root exports `loadExtensionFromFactory`, ideally with a way to run `exec` elsewhere, or `DefaultResourceLoader` loads inline factories without scanning; the first request standing for a run's start when pi-durable has a hook where a run starts; the package's own prompt layout when Pi exports one for extensions' additions alone; loading add-ons in the host when the add-ons in use pin themselves (napi-rs 3.12.1 and later); the facades when the runner's parameters become interfaces; the one-Harness rule when hooks and tools learn their Harness; the required default selection when pi-durable can install an extension that only the conversations naming it select; the scheduler if Effect gains a pool that places borrowers without capping them; a bundle cache if prepare comes to run per job or the build grows slow; a limit on reopens for a conversation whose own calls keep ending workers, if that is seen.
