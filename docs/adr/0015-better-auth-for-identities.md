# Better Auth provides members, sign-in and API keys

The hub's identities come from Better Auth on the hub's Postgres, in the hub's schema. Members sign in with an email and password or through the organization's identity provider (OIDC first, SAML later), and a deployment can turn passwords off once SSO is in place; the CLI signs in with a device login. Services and runners use organization-owned API keys that are named, carry permissions and are revocable. The key management routes declare `byMember` so an API key cannot reach them. Only owners and admins hold the permissions the hub checks when listing keys (`apiKey:read`) and Better Auth checks when creating or deleting them. Every job records who submitted it. Better Auth's organization, API key, SSO and device authorization plugins cover these needs without authentication code of our own.

A new hub gets its Organization and owner in one of two ways, both ignored once the Organization exists. Without settings for the owner, the hub prints a setup link, on Docker at each start and on Workers from the `vp run setup` deploy step, as Jupyter prints its token and Jenkins its initial admin password; whoever opens it names the Organization and creates the owner in the dashboard. Only someone who can read the hub's output has the link, which matters because a Workers hub is reachable by anyone from its first deploy; for that reason `vp run setup` prints it only when stdout is a terminal. CI runners that allocate a terminal can still log the link. Its token comes after `#`, so it stays out of request logs and `Referer` headers; it works once and for a day, a new link replaces it, and the hub keeps it by its digest in Better Auth's `verification` table, where Better Auth keeps its own one-time values, through the internal adapter its plugins use. With `ADMIN_EMAIL` and `ADMIN_PASSWORD`, as Grafana, Authentik and Keycloak take theirs, the hub creates the owner itself, for automated deploys and the CLI's stack; one without the other is refused. Either way a Better Auth instance built on one database transaction, as Better Auth cannot join one it did not open (better-auth/better-auth#10609), creates the owner and the Organization, so a failure, such as a password Better Auth refuses, leaves neither behind and the link usable, and of two setups at once one gets through and the other finds the hub set up. A forgotten password is reset with a command run with database access, as with Grafana's `grafana cli admin reset-admin-password` and GitLab's `gitlab:password:reset`, since database access is what only those running the hub have. Once passwords can be turned off, recovery also needs a temporary admin who signs in without the identity provider, as Keycloak's `bootstrap-admin` creates, since a broken provider would otherwise lock every member out.

After setup, an owner or admin invites a person to join with a role they can grant. Better Auth issues the invitation. Resending a pending, unexpired invitation renews the same ID for 48 hours. After expiry, resending issues a new ID, so the inviter shares the ID the resend returns. The hub lets its holder preview the address, role, Organization and expiry before signing in. Acceptance claims the pending invitation by deleting it in the same transaction that adds the member. Deleting it means a later cancellation cannot overwrite a successful redemption. The hub holds the inviter's membership through acceptance. Preview and `GET /invitations` also check the inviter's current authority. Only owners see invitations granting owner in the list. Better Auth's own list remains available and can show invitations whose inviter has lost authority. Acceptance checks the inviter again and refuses those invitations.

The hub uses the inviter's current authority to decide which invitations are live. It refuses a plain re-invite if the address has a live invitation in the Organization whose role the caller could not grant. To cancel an invitation by ID, the caller must be able to grant its role regardless of its state. The hub accepts the window between each check and its write because an invitation or membership would have to change during the caller's request, and the caller cannot control when that change commits.

A new account takes its address from the invitation. An existing account must present its own session. The transaction's Better Auth instance uses the serving instance's signing settings so it can verify that session. Better Auth checks the new password and the membership limit. A refusal rolls back the claim, the account and the membership together.

Better Auth runs inside the Workers hub with a fresh instance per request and its runtime schema check off. better-auth/better-auth#10315 describes auth calls hanging in a Workers isolate after a cancelled request leaves a promise shared across requests unsettled; 1.7.8 fixes the module-level part and 1.7.21 the runtime schema check (better-auth/better-auth#11651), and instances built per request avoid the rest. Rate-limit counts are kept in the database, so they hold across hub replicas and Workers isolates, and the header carrying the client's address is a deployment setting, because a proxy that rewrites `X-Forwarded-For` puts every client into one bucket.

Leaving or removal ends the membership and leaves the account and session valid. An identity provider can create an account independently of an invitation. Better Auth joins the session to its user in one read. Its custom session then reads the deployment's Organization and the user's membership together, so a missing Organization and a removed member have distinct answers. A member's session includes the Organization's ID and name and the member's role. The hub's guard consumes that result. The dashboard reads the same session on navigation, including for an account that can still change its password after removal. The hub authorizes the request against the Organization plugin's static roles. A dashboard page can use `authClient.organization.checkRolePermission` with the role from a member's session and the same role definitions.

## Considered options

- Writing our own token handling: small at first, but members, SSO, scoped keys and device login together are a large, security-sensitive subsystem.
- Cloudflare Access in front of the hub: it cannot protect a hub on localhost or outside Cloudflare, so it stays an optional outer layer for deployments that want it.
- Sign-in through an identity provider only, as Tailscale does: small teams and local development often have no provider, and self-hosted tools such as Grafana and GitLab offer passwords with a switch to turn them off.
- A first visit open to anyone, as n8n and Metabase offer: a Workers hub is public from its first deploy, so a stranger could claim it, and attach Runners to its database, before the operator does.
- A setup code issued only by an explicit operator command and valid for minutes: it keeps the code out of logs, but adds a step every operator must find, while the link appears where the operator already looks when starting the hub; a link a day old in a log is worth no more than access to that log.
- A table of the hub's own for the token: Better Auth's `verification` table already keeps one-time values with an expiry, consumes them atomically and can store them by their digest.
- Only environment variables, as before the dashboard: they remain for automated deploys, but a person setting up a hub by hand should not have to put a password in a file.
- Environment variables that set the owner on every start (n8n's opt-in mode): rare, and it makes the environment a second source of truth for a member managed in the hub.
- A typed `GET /me` would need to call Better Auth with `returnHeaders: true` and forward `Cache-Control: no-store` and `Pragma: no-cache` on every response, along with each `Set-Cookie` header on renewal. A 403 from the member guard also omits the account, so a removed member's pages would need a second request. Better Auth's session endpoint already preserves the renewal headers and the account.
- A permission flag per feature in the session would change its response with every new feature. The role and the shared role definitions already answer those checks.
- Gating Better Auth's public sign-up route with a hook would make closure depend on the hook. A user-creation hook runs after duplicate detection and password hashing. Even an endpoint hook would still have to coordinate registration and membership. Keeping public sign-up disabled and calling it inside the claim transaction gives both writes one outcome.
- Deleting the account on departure would treat membership as the lifetime of an identity that SSO can create independently. The account holder can sign in again to accept a fresh invitation.
- Better Auth's `get-invitation` and `accept-invitation` both need the recipient's session. A new invitee has no account to sign in with. Native acceptance also writes the invitation's status before the membership transaction, so it cannot commit a new account, membership and claim together.
- Requiring cancellation before re-inviting an address would also apply to pending, unexpired invitations hidden from the caller because the inviter lost authority or the caller could not grant the role. Someone able to grant that role would have to find the invitation in the Organization's full list and cancel it by ID, so the hub keeps replacement enabled for authorized callers to re-invite in one step.
- Cancelling outstanding invitations on demotion or removal would add writes to every path where an inviter can lose authority. Acceptance would still have to check the inviter's authority because a demotion can race it.
- The native Organization invitation list reads at most 100 rows and includes expired invitations. Closed rows can fill that read while live invitations are missing.
- Locking the three library routes would protect only writes through those routes. The database trigger also covers writes from older Workers and account-deletion cascades.
- Storing a digest of the invitation ID would prevent an inviter from copying the original ID again and require a different way to issue and list invitations. Database read access alone otherwise yields no usable password, API key or signed session cookie. A readable pending invitation adds a credential to that database. For a new address its holder can claim the invited membership before the intended recipient. Expiry 48 hours after creation or the most recent renewal and restricting database and backup access to operators bound the accepted risk.

## Consequences

A new dashboard document makes two session requests. The navigation loader awaits `getSession()`. The cross-tab watcher subscribes to `useSession` (ADR 0046), which fetches on mount. Better Auth's `hydrateSession()` supplies data for the first render and still allows the mount fetch. The store's `refetch()` returns no session for a loader to use.

Better Auth's tables share the hub's schema and naming (ADR 0020); its CLI drafts them into hand-written migrations. `better-auth` and `@better-auth/api-key` are pinned to one version together, and every upgrade re-runs the draft. Better Auth signs members in only from the hub's own origin once a request carries browser fetch metadata, as Node's `fetch` does, so the dashboard is served from the hub's origin. Better Auth answers a key lacking a permission as it answers an unknown key, with 401, so the answer reveals nothing about the key.

The Organization keeps at least one owner. Better Auth's last-owner check returns HTTP 400. If concurrent departures or demotions both pass that check, the database rejects the losing write at READ COMMITTED and Better Auth returns HTTP 500. Translating that failure would require wrapping the library's adapter or rewriting its responses, for a race the database already makes safe. Organization keys survive a departure, and the keys list identifies the creator and whether they still belong.

Every route of Better Auth and its plugins is served under `/api/auth/*`, so the hub turns off those for what it wraps with rules of its own (API keys and invitation redemption) and Organization deletion, and adding a plugin includes reviewing the routes it brings. Better Auth records no creator for organization-owned keys, and its audit logs come only with its paid hosted service; the hub records who did what in its own data, starting when a feature needs it, such as jobs recording who submitted them.

## When to reconsider

If deployments can define roles dynamically, the hub and dashboard will need the deployment's current permissions to check a member's role.

Reconsider keeping readable invitation IDs if invitations can stay pending without anyone renewing them or anyone outside the operators handles database backups.
