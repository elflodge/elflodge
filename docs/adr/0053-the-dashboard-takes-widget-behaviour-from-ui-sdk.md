# The dashboard takes widget behaviour from UI SDK

Some of the dashboard's controls need behaviour no plain element gives. A confirmation that removes a Runner or revokes a key sends a request and waits for the hub: while it waits, its confirming button must take no second press and keep the focus, the wait must be announced, and the member must not lose the answer. Afterwards focus must land somewhere useful, also when the row whose button opened the dialog is gone. Written by hand over the native `dialog`, each confirmation kept its own pending and failure state, restored focus that disabling a button had lost, waited for a later read to drop the row before moving focus, and, because Escape could close the dialog while its request ran, needed a second place on the page to report a refusal that arrived after.

That behaviour comes from Vercel's UI SDK, `@ui-sdk/solid` on its framework-free core `@ui-sdk/core`, published for Solid 2. Its parts own the running action, dismissal, focus on opening and closing, the inert page and the announcements, with the ARIA each needs, and render no styles: the dashboard's own stylesheets style them through their `data-slot` attributes. The little CSS UI SDK adds sits in its cascade layer, `ui-sdk`, which the dashboard's rules, in no layer, beat whatever the order; `app.css` declares it first, as UI SDK's docs ask, so it also stays below any layer added later. The dashboard keeps what is its own: the words, the requests, the rules of the product such as "already gone" after a 404, its notices and when it reads again.

A confirmation on a list is one alert dialog for the list, `ConfirmDialog`, outside it, opened by a trigger part in each row that carries the record as the dialog's payload. An async action on its confirming Close part runs the request: a rejection keeps the dialog open with the reason in the part's state, and a resolution closes it with focus on the page's notice of the outcome. While it runs, Escape and the keeping button are refused, so a member never leaves a confirmation whose answer has nowhere to show. Its content renders into the body through UI SDK's `container`, beside the page's root: UI SDK makes inert what is beside the dialog when it opens, so the page is then inert, what a read renders after it opened included, except notices already showing and what holds them, which UI SDK keeps live. So with an earlier notice showing, content a read renders later can be exposed beside the dialog; the dialog still carries `aria-modal`, keeps focus inside and takes outside presses.

The page reads its list everywhere through `latest(() => deep(query.data))`, as the job page reads its job. That holds for a query that reads again under the same key, by a poll or an invalidation; a change of key is a navigation and shows its own loading state, and read through `latest` it would show the new key beside the old data. While a query that has data reads again, Solid Query's `data` is a pending value, and Solid can hold a write with a render pass that reads a pending value until the read lands. With the list read directly, a confirmation's "Working…", its failure and its closing waited for the list's poll or reread. Probes found both sides of the page matter: with only the rows reading the list directly, its opening waited; with only the list's `Show` and the short IDs, its "Working…" did. A held read in the shell, the hub strip's counts, held nothing.

Since the member cannot leave a running confirmation, a request the hub never answers must end by itself. A call to the hub's API ends when the hub has not answered it in 30 seconds, through oRPC's `TimeoutLinkPlugin`, except the calls whose request carries what a member submitted: uploading a file, creating a Batch and adding jobs to one, which take as long as the member's connection needs, on pages the member can stop or leave. Better Auth's client sets better-fetch's `timeout` to the same 30 seconds, which covers a call made without a signal of its own, and only until the answer's headers arrive, as the shell's session read in `beforeLoad` is. The session store's read and renewal, and the members read, pass their own signal, so they have none. No confirmation on Runners or API keys waits on Better Auth's client.

A confirmation shows the hub's words only for a refusal, an answer with a 4xx status, after which nothing was done. Any other failure, no answer, a 5xx from the hub or a proxy, or an answer that fails the contract check, may have come after the write was done, so it says the dashboard could not confirm it and to check before trying again. After a 404, one read of the list through the API client, within the same deadline, not tried again and not paused offline, decides whether the record is already gone, after older reads of the list are cancelled; its answer then replaces the list, marked stale so the next read fetches it, rather than reading at once, which would hold that answer back until the read ends. It bypasses Query because `queryClient.query` with its own `retry` and `networkMode` leaves them on the query, and an invalidation, which fetches with the query's options, would use them until the page's observer reads again.

UI SDK is a 0.1 beta, so its version is pinned exactly and each upgrade reads its changes.

## Considered options

- Behaviour written by hand over native elements, as before: `dialog` has no state for a running action, so every dialog carried its own, with its own focus repairs, and a refusal after a dismissal had nowhere to show but the page.
- Ark UI 6 on Zag 2: its dialog models only open and closed, leaving the running action to each caller as before, and its Solid 2 build was not published.
- UI SDK's shared `confirm()`: it takes strings and answers a boolean, so it cannot hold the request, a heading with markup, or a failure line.
- A dialog in each row: it goes with its row when a read drops the record, and a refusal still to come shows nowhere.
- A deadline passed by each confirmation for its own request: Query gives a mutation function no signal, and a form or a control waits on the hub as a confirmation does.

## Consequences

The first page that uses UI SDK loads about 30 KiB more of gzipped JavaScript, in a chunk only the pages that use it load; later parts share its core. UI SDK adds its CSS to the page: under a Content Security Policy without `'unsafe-inline'` styles it takes the policy's nonce from a `csp-nonce` meta tag, and with the tag but no nonce it adds constructed style sheets, which no policy blocks. A member waits at most 30 seconds for an unanswered write before the confirmation can be left, and after a 404 at most 30 seconds more. Every page that holds a UI SDK part reads the queries it polls or invalidates through `latest`. Dialogs still written on the native element keep their own behaviour.

## When to reconsider

When UI SDK stops publishing for the Solid release the dashboard runs on, or a pinned upgrade keeps breaking its parts' behaviour. When a part the dashboard needs is missing and its core cannot build it. When a call needs a deadline other than 30 seconds or none. When Solid Query's `data` no longer goes pending while a query that has data reads again, the lists can read it directly.
