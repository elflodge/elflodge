# The dashboard takes widget behaviour from UI SDK

Some of the dashboard's controls need behaviour no plain element gives. A confirmation that removes a Runner or revokes a key sends a request and waits for the hub: while it waits, its confirming button must take no second press and keep the focus, the wait must be announced, and the member must not lose the answer. Afterwards focus must land somewhere useful, also when the row whose button opened the dialog is gone. Written by hand over the native `dialog`, each confirmation kept its own pending and failure state, restored focus that disabling a button had lost, waited for a later read to drop the row before moving focus, and, because Escape could close the dialog while its request ran, needed a second place on the page to report a refusal that arrived after.

That behaviour comes from Vercel's UI SDK, `@ui-sdk/solid` on its framework-free core `@ui-sdk/core`, published for Solid 2. Its parts own the running action, dismissal, focus on opening and closing, the inert page and the announcements, with the ARIA each needs, and render no styles: the dashboard's own stylesheets style them through their `data-slot` attributes. The little CSS UI SDK adds sits in its cascade layer, `ui-sdk`, which the dashboard's rules, in no layer, beat whatever the order; `app.css` declares it first, as UI SDK's docs ask, so it also stays below any layer added later. The dashboard keeps what is its own: the words, the requests, the rules of the product such as "already gone" after a 404, its notices and when it reads again.

A confirmation on a list is one alert dialog for the list, `ConfirmDialog`, outside it, opened by a trigger part in each row that carries the record as the dialog's payload. An async action on its confirming Close part runs the request: a rejection keeps the dialog open with the reason in the part's state, and a resolution closes it with focus on the page's notice of the outcome. While it runs, Escape and the keeping button are refused, so a member never leaves a confirmation whose answer has nowhere to show. Its content renders into the body through UI SDK's `container`, beside the page's root: UI SDK makes inert what is beside the dialog when it opens, so the page is then inert, what a read renders after it opened included, except notices already showing and what holds them, which UI SDK keeps live. So with an earlier notice showing, content a read renders later can be exposed beside the dialog, and a press there moves focus to it and makes the pressed button where focus returns after Keep it. A row's trigger pressed there cannot hand the open dialog its record: `ConfirmDialog` cancels a payload change while the dialog is open, through UI SDK's `onPayloadChange`, so the dialog keeps its record and its running request.

A record's controls, as on a job's page and a Batch's, share one `ConfirmDialog` for the page, outside every part a read can switch. The job page's triggers pass the action as the payload; the Batch page's Cancel passes the counts of unfinished and status-unknown jobs taken at the press, so the dialog's figures stay as they were. When a read takes the action away, its `withdrawn` replaces the explanation and the confirming button, UI SDK's `Button` disabled with `focusableWhenDisabled`, keeps the focus and does nothing. The explanation is a polite live region the dashboard sets itself, off while the action runs, since it is rendered text a read changes, where UI SDK's `announce` is for an action's result with no element of its own.

What a confirmation's interaction reads from the page's list, or makes Solid recompute, is read through `latest`: the trigger's payload and label taken from a row, the conditions that show the triggers, what the dialog renders and what the confirmed action recomputes. Runners and API keys read the whole list as `createMemo(() => latest(() => deep(query.data)))`, as the job page reads its job; reading just the fields needed inside `latest` serves as well. While a query that already has data reads again under the same key, by a poll, an invalidation or a refresh on return to the tab, Solid Query makes `data` a pending value. Solid stages plain writes until the end of a flush, and a flush that reruns a derivation of that pending value joins the transaction waiting for it, so every write staged in that flush waits for the read, UI SDK's state included. Where the derivation sits among the components or in the DOM does not decide it: with the rows reading the list directly, a confirmation's opening waited for the poll, and with only the list's `Show` and the short IDs, its "Working…" did. A reader the interaction does not touch, the hub strip's counts, reads directly and holds nothing. A query whose key changes keeps its own loading state: through `latest` it would show the old record's data beside the new id.

A form in a dialog that writes to the hub, `FormDialog`, is locked the same way while its request runs: Escape and the dismissing button do nothing, and the form sends nothing more. As with a confirmation, the lock holds against the dialog's own means of leaving, Escape, its buttons and a press outside it; the browser's Back or leaving the page still leaves it. It is UI SDK's dialog, for a focused task over the page, rather than its alert dialog, which asks a question that needs an explicit answer. Its form is an ordinary one sent through the dashboard's `createFormAction`, which UI SDK's dialog leaves to the page, and the dialog's `dismissible` follows that action's pending state. Left open to dismissal, as the native dialogs it replaces were, what the hub created after a dismissal, such as a key it shows only once, would be shown nowhere, and a form opened again could send the same write twice. A new key or invitation link takes the form's place in the same dialog and is held in the dialog's content, which UI SDK removes when the dialog closes. Rename, Change role and Resume with a budget close on success and focus the page's notice, the job's status for Resume. An unchanged role sends nothing and returns focus to the trigger. A failure is worded as a confirmation's, below.

Add Runner has instructions, a command to copy and a live registration status. Creating a registration key changes the command and its note in place and has no fields, so the action belongs in the body of a Dialog. Its Button holds further presses and announces a slow request. The dialog keeps the member with the answer while the request runs. Only its mounted content holds the returned key. Focus moves to Copy, described by the shown-once note. As in Create key, an error from key creation passes through `secretAnswerFailure` before logging because an unreadable answer can contain the key.

Since the member cannot dismiss a dialog waiting on a write, a request the hub never answers must end by itself. A call to the hub's API ends when the hub has not answered it in 30 seconds, through oRPC's `TimeoutLinkPlugin`, except the calls whose request carries what a member submitted: uploading a file, creating a Batch and adding jobs to one, which take as long as the member's connection needs, on pages the member can stop or leave. Better Auth's client has no deadline of its own: with one, the shell's session read in `beforeLoad`, which is not tried again, ended on its error page when a jump of the clock fired the timer while the read was under way, as a test of the hub strip does. On the Organization page, Remove, Leave, Revoke, Rename, Invite and Change role wait on Better Auth. Remove and Change role also read the members once when the hub answers “Member not found”. Each call passes `fetchOptions: { timeout: HUB_DEADLINE_MS }` to better-fetch. A call the hub does not start to answer within 30 seconds ends. A response body that stalls after its headers would still hold the dialog. Session and list refreshes run in the background.

A confirmation shows the hub's words, and a form dialog places the hub's issues at its fields, only for a refusal, an answer with a 4xx status, after which nothing was done. Any other failure, no answer, a 5xx from the hub or a proxy, or an answer that fails the contract check, may have come after the write was done, so it says the dashboard could not confirm it and to check before trying again. After a 404, one read of the list, within the same deadline, not tried again and not paused offline, decides whether the record is already gone. Better Auth answers a missing record with a 400 and a code: its "Invitation not found" alone says the invitation is gone, with no read, while its "Member not found" also answers a reader who is no longer a member, so one such read of the members decides which. That read establishes one fact, so only that is written: when it omits the record, reads of the list still running are cancelled, since one started before the removal could bring the row back, and the record is taken out of the cached list, which a read that landed meanwhile may have made newer than the check's answer. The list is then marked stale so the next read fetches it, rather than read at once, which would hold the written list back until that read ended. When the record is still listed, nothing is written. It bypasses Query because `queryClient.query` with its own `retry` and `networkMode` leaves them on the query, and an invalidation, which fetches with the query's options, would use them until the page's observer reads again.

A single form control gets its accessible name and description from UI SDK’s Field. FieldLabel connects the label to the control, and FieldDescription connects the hint and, when present, the refusal. The field’s invalid state follows the refusal. Passing false when it clears reserves the dashboard’s failed colour and focus target for a refusal. The browser still shows its validation bubble because the field has no inline validation error part. When several fields are refused together, the form focuses the first unless the member moved on. Focus reads that control’s hint and refusal together. FieldError with `match` also sends the words to a shared live region. Each write replaces the one waiting there, so focus on the first field would be followed by the last field’s refusal without its name.

Text and multiline text use Input and Textarea. A native password input joins the field through FieldControl because both Input and PasswordInput keep typed text in their store. Native select, number and date controls join the same way to keep the browser’s pickers and number spinner. Checkboxes and radios retain the browser’s marks, and the draft file chooser supplies files to the existing job rows. A fieldset can itself be refused and focused. It keeps its own description because UI SDK’s FieldSet has no part for a refusal on the set.

UI SDK is a 0.1 beta, so its version is pinned exactly and each upgrade reads its changes.

## Considered options

- Behaviour written by hand over native elements, as before: `dialog` has no state for a running action, so every dialog carried its own, with its own focus repairs, and a refusal after a dismissal had nowhere to show but the page.
- Ark UI 6 on Zag 2: its dialog models only open and closed, leaving the running action to each caller as before, and its Solid 2 build was not published.
- UI SDK's shared `confirm()`: it takes strings and answers a boolean, so it cannot hold the request, a heading with markup, or a failure line.
- A dialog in each row: it goes with its row when a read drops the record, and a refusal still to come shows nowhere.
- Form dialogs that can be left while the hub answers, as the native ones were: an answer that arrives after a dismissal, such as a new key, is shown nowhere, and a form opened again can send the same write twice.
- A form dialog sent by a Close part's `action`, UI SDK's documented way to hold a dialog open while a request runs: the Close part is a `type="button"`, so it cannot submit a form or run the browser's validation, and it closes the dialog once the action resolves, which would drop an answer shown in it.
- A deadline passed by each confirmation for its own request to the hub's API: Query gives a mutation function no signal, and a form or a control waits on the hub as a confirmation does. Better Auth's calls take one each because a deadline on its whole client ends the shell's session read too.

## Consequences

The default error page offers a retry Button, so the dashboard entry loads Button and its shared core (about 12 KiB of gzipped JavaScript). Pages that open an alert dialog load its additional chunk (about 20 KiB). UI SDK adds its CSS to the page: under a Content Security Policy without `'unsafe-inline'` styles it takes the policy's nonce from a `csp-nonce` meta tag, and with the tag but no nonce it adds constructed style sheets, which no policy blocks. A member waits at most 30 seconds for an unanswered write to the hub's API before the dialog can be left, and after a 404 at most 30 seconds more. A Better Auth call that the hub does not start to answer within 30 seconds ends, as does the separate check for a member who is already gone, but an answer that stalls after its headers would still hold the dialog. The sign-in and setup route loaders read setup status directly, once. When the 30-second deadline expires, the loader shows its error page with Try again. The retry Button can hold focus and announce a slow read while the router keeps it mounted. Reads through Query follow its retry policy. Every page that holds a UI SDK part reads through `latest` what its parts' interactions read or recompute from a query.

## When to reconsider

When FieldError can deliver a refusal on focus without a competing announcement, it can replace the second FieldDescription. When UI SDK stops publishing for the Solid release the dashboard runs on, or a pinned upgrade keeps breaking its parts' behaviour. When a part the dashboard needs is missing and its core cannot build it. When a call needs a deadline other than 30 seconds or none. When Solid Query's `data` no longer goes pending while a query that has data reads again, the lists can read it directly.
