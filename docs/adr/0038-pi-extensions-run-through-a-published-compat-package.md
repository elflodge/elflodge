# Pi extensions run through a published compat package

Pi coding-agent extensions run on pi-durable through `@elflodge/pi-durable-compat`, a package of its own in this workspace, published with the same version as the rest (ADR 0032). It imports nothing of Elflodge, so any pi-durable host can use it; pi-durable has no way to run coding-agent extensions itself (earendil-works/pi#10386).

A host prepares the extensions once: Pi's own package manager installs them, as `pi install` does, and Rolldown bundles them with the package's runtime into one build, treating Pi's packages as free of side effects so only the parts in use remain, except three modules whose import registers pi-ai's image providers and sets the default stream function of Pi's `Agent`, found by listing every import-time statement in Pi's modules. The entry of each extension installed in the host's directory is written beside its source, so the files a package reads relative to it (its `package.json`, templates, WebAssembly) are found; extensions from local paths elsewhere and shared chunks go in a directory of their own, with TypeBox in a chunk of its own, which breaks a cycle of top-level awaits one extension otherwise deadlocks on. Native add-ons stay where they are installed, and the host loads each in its main thread before starting workers: Node unloads a worker's add-ons when it exits, and one with a thread-local destructor left behind then crashes the process (zhangyuang/node-ffi-rs#145); one the process holds is never unloaded. Photon, Pi's image library, which reads its WebAssembly beside its module, also stays installed. The build runs in a child process: in a worker thread, Rolldown's native runtime, its threads and their memory stay in the host process after the build, about 775 MiB unused. The bundle resolves Pi's packages as Pi's loader does for extensions, from the package's own copy of the coding agent, with pi-ai's root as Pi's extension view of it and Pi's former package names. Extensions run in a few worker threads shared by all conversations, with one instance of each extension per conversation. A conversation's instance is created when the host attaches it. The host installs one pi-durable extension per registry, `pi-durable-compat`, with every attached conversation's tools and only the hooks some extension listens to, and its tools and hooks act for the attached conversation they run in. pi-durable selects every installed extension for every conversation by default and lets a later tool replace one of the same name, so extensions installed per conversation would take each other's tools. Hooks and tools know only their conversation's ID, which is unique within one Harness, so a registry serves one Harness.

In the worker, Pi's own loader builds the `pi` object each extension's factory receives (`loadExtensionFromFactory`, which Pi's root does not export), reached by its file path in the package's own copy of the coding agent, with `PI_PACKAGE_DIR`, Pi's documented override, defined in the bundle as that copy's directory, since Pi otherwise looks for its own files beside its code, which the bundle moves, with `exec` replaced to run in the host's environment and `on` wrapped to tell the host of a subscription made after loading. Pi's root reaches its loader only through `DefaultResourceLoader`, whose every load scans the working directory, its ancestors and the user's home for skills and settings, and which adds about 18 to 21 MiB per worker, measured twice. It dispatches events through Pi's exported `ExtensionRunner`, so handler order, how results combine and how a failing handler is isolated are Pi's own, and follow Pi's releases. The runner takes Pi's `SessionManager` and `ModelRegistry` classes, which it only hands to extensions as `ctx.sessionManager` and `ctx.modelRegistry`; the package passes objects with the methods extensions use, over the host's journal and models, with one type assertion each. Reads of the history and the agent are synchronous in Pi, so the worker waits for the host's answer (`sync-message-port`); the host never waits for a worker, and pi-durable runs hooks off its Session line, so a handler can read the history too. Writes such as `appendEntry` travel on the same channel and the host carries them out before a later read, so an extension reads what it just wrote, as in Pi. pi-durable runs a tool's `prepareArguments` synchronously on the host, so for a tool that has one the host parses arrays and objects sent as JSON text, and the worker runs the tool's own before executing.

The host runs Pi's lifecycle events from pi-durable's hooks, installing only those some attached conversation listens to. pi-durable has no hook where a run starts, so a run's first request stands for it: it runs `before_agent_start` and `agent_start` once, describing the run by the oldest of the inputs pi-durable placed for it (`LiveRun.inputs`, each read through its submission), and not for a continuation after an answer or a `continue` after a failure, and records what they return as a memo of the generation task, so a retry or a crash sends the same additions without running them again. What handlers add to the system prompt goes into each of the run's requests as sections of its system message, laid out by the package as Pi lays out those parts, since Pi's own function builds its whole prompt with its default rules among the guidelines, kept in memory for the run's later rounds, which a host that restarts mid-run sends without them; the messages they return go with the first request and are written to the conversation, where they land after its answer; a tool selection they change, or `setActiveTools`, configures the conversation's model tools, which a request fixes before its hooks run, so it applies from the next request. A returned `systemPrompt` is ignored, since pi-durable builds the prompt. `turn_start`, `message_end`, `turn_end`, `agent_end` and the tool execution events are observed from the generation and tool hooks, their results ignored; `agent_end` follows only runs that answered, as `afterRun` does. `session_before_compact` maps to `beforeCompact`: a cancel declines, a custom summary replaces pi-durable's. Extensions that register model providers are not supported: the host makes model calls with its own models, and a provider an extension defines would have to run on the host.

Measured with `pi-web-search` and `pi-web-access`, PSS per worker on Node 26: about 99 MiB loaded as shipped, 24 bundled, and 35 to 39 in a host, with the runtime, Pi's runner and a conversation.

## Considered options

- A process per conversation, or extensions loaded as shipped: about 99 MiB per instance or worker, for a Runner that hosts hundreds of conversations.
- Building the `pi` object with code of our own, filling Pi's exported `Extension` record as its loader does: about 300 lines that repeat Pi's loader and drift from it with each release. Reaching the loader by path instead pins it to the package's own copy of Pi, so a release that moves the file fails the type check and the build rather than drifting.
- Pi's loader through `DefaultResourceLoader`'s `extensionFactories`: the disk scans and the memory above.
- One pi-durable extension per conversation: under pi-durable's default selection, the conversations' tools replace each other.
- The host selecting each conversation's extension with pi-durable's `extensions` setting: every host would have to set its default selection and handle the conversations a conversation creates.
- One bundle directory for all entries: an extension that reads a file next to its code, or its own `package.json`, does not find it.
- Describing the run by the entries it started with: entry kinds and order mistake a compaction's summary or a message written meanwhile for the prompt, and cannot tell which of several inputs started the run.
- Running `before_agent_start` when the host submits input: it misses runs that queued input, an extension's message or a continuation starts.
- Prompt additions as a pi-durable prompt section: sections render before the request's hooks run and cannot carry messages.
- Building in a worker thread: at 100 conversations the process held 867 MiB, against 230 with the build in a child process; a child takes about 50 MiB more than a worker thread while it runs.
- Caching the bundle between starts: a key that misses a change, such as an upgrade of this package or an edited local extension, runs an old build, to save about a second at start.
- Dispatching events with code of our own: about 400 lines that repeat Pi's runner and drift from it with each release.
- A real `ModelRegistry` in each worker: it needs Pi's `ModelRuntime`, which loads every built-in provider, about 29 MiB more per worker.
- A synchronous call from the host to the worker for `prepareArguments`: a host waiting on a busy worker would stall every conversation.
- Effect's RPC and worker modules for the calls between host and workers: they would load Effect into every worker, which loads only the extensions and the parts of Pi they use, for what birpc does in 7 KB.
- Effect's `Pool` for the workers: it caps how many borrowers an item takes and makes the rest wait, while a conversation keeps its worker for as long as it runs.

## Consequences

Extensions run with the host process's permissions; a worker thread is not a sandbox. Bundled code reads files relative to the file it is bundled into, so code that moves to the bundle's directory finds none of its package's files. Extensions that start Pi as a process of their own, such as `pi-subagents`, are not supported. Module-level state is shared by the conversations on a worker. An extension that does not bundle is not loaded. A tool's own `prepareArguments` runs after pi-durable has validated the arguments. The package takes only patch releases of the coding agent, since it relies on internal files a minor release may move (its loader, its extension view of pi-ai, the modules whose import registers providers), so each Pi minor needs a tested release of the package, which also rechecks the coding agent's dependencies left installed, such as Photon; pi-durable, pi-ai and chord are peers on their public APIs and keep a caret range. When pi-durable can run coding-agent extensions itself, the package's README points to it.

Reconsider reaching Pi's loader by path when Pi's root exports `loadExtensionFromFactory`, ideally with a way to run `exec` elsewhere, or `DefaultResourceLoader` loads inline factories without scanning; the first request standing for a run's start when pi-durable has a hook where a run starts; the package's own prompt layout when Pi exports one for extensions' additions alone; loading add-ons in the host when the add-ons in use pin themselves (napi-rs 3.12.1 and later); the facades when the runner's parameters become interfaces; the one-Harness rule when hooks and tools learn their Harness; the scheduler if Effect gains a pool that places borrowers without capping them.
