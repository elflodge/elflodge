# Job commands reach the internet, but not local or private addresses

A job's commands reach the public internet. Jobs install packages, call public APIs and fetch what their instructions point to, and a job that cannot do so works around it in ways that cost more and succeed less, or fails. What a Runner must keep from its jobs is what the internet does not already offer them: the Runner's own host, where its data, its credentials and services listening on loopback are, and the networks the host can reach that the internet cannot, where internal services often answer without authentication. So the default refuses destinations by address: `localhost` and the host's interface addresses; loopback, link-local and cloud metadata addresses, including Azure's `168.63.129.16`, which is in public space, the other endpoints being in refused ranges; private and shared address space; and the other rows of IANA's IPv4 and IPv6 special-purpose registries whose "Globally Reachable" is False, with multicast. Rows the registries mark globally reachable, or N/A, stay open. `::ffff:0:0/96` is not listed: a `BlockList` reads that range as every IPv4 address, and an IPv4-mapped destination is judged by the IPv4 address it carries.

An operator opens ranges with `RUNNER_NETWORK_EXCEPTIONS`, for every job of the Runner: a Runner serves one organization, whose operator knows which internal services its jobs may use, and a setting per job would be a policy each caller could widen. An entry opens every port, or, for a single address, the one port it names, written as sandbox-runtime writes a destination (`10.0.0.5:8080`, `[fd00::5]:8080`), so that one service, such as a search provider the operator runs, can be opened without the rest of its host. A range takes no port: sandbox-runtime's allow list takes ports only with single addresses, so a name resolving into a range on a port would be refused, which the operator would learn only from a job's refusal, and one service across many machines is usually reached by name. A range opens IP destinations in it and names that resolve into it; a name alone opens nothing, as whoever controls a name's DNS decides where it points. A range opens the addresses it covers, the host's own included: an operator who opens a range holding a host address has opened the host there, and one who means less writes a narrower range. Loopback, link-local and cloud metadata addresses are the exception, the host's own among them, opened only by an entry naming the address alone, as are the other classes sandbox-runtime's guard holds back, multicast, broadcast and unspecified: nobody knows which addresses inside shared or unique-local space are a cloud's metadata service, which gives out the instance's credentials, so an operator opening `100.64.0.0/10` for Tailscale has not chosen to open Alibaba Cloud's `100.100.100.200`. `/0` is refused, as it would open everything, the default's refusals included. `RUNNER_NETWORK=none` is for operators whose jobs must not reach the web: it refuses web access, any request to a destination the job picks, while search, a request to a provider the operator chose, which decides for itself what to contact, keeps working, with the page text a provider returns beside its results. A page a fetching service retrieves for a URL the job gave counts as web access, as the URL alone can carry data out. Both settings are enforced by the sandbox, so a Runner that would run jobs without one refuses to start with either.

sandbox-runtime enforces it, as it already confines the jobs (ADR 0027): every command reaches the network only through its proxies, which decide each destination from its process-wide configuration. The Runner's part is that configuration and its ask callback. Open, the deny list is empty and the allow list holds only single addresses, so nearly every destination reaches the callback. The callback judges an IP destination itself: it refuses one among the host's addresses, read at each request as the guard reads them for names, or in a refused range unless an exception covers it on every port (one on a single port is in the allow list, which sandbox-runtime matches first), with a reason that names what is refused and the setting that opens it. An address in the guard's own classes that an exception covers must also pass a second resolved-address guard holding only sandbox-runtime's own classes and the allow list, which applies to it the rule the guard applies to names, with sandbox-runtime's own list of metadata endpoints. sandbox-runtime gives the callback the destination as the client wrote it, so the callback reads it with sandbox-runtime's own `canonicalizeHost`, imported from its `dist` as the package's main entry does not export it, which is how `127.1`, `2130706433` and `[::ffff:127.0.0.1]` are refused as `127.0.0.1` is. An IPv6 address carrying an IPv4 one that a network delivers to it, such as NAT64's `64:ff9b::a00:5` or 6to4's `2002:a00:5::`, is refused as that IPv4 address is too, read with sandbox-runtime's `embeddedIPv4` as its guard reads names; only the address itself is matched against exceptions, so opening `10.0.0.0/8` does not open its NAT64 form as a typed address, though the guard lets a name resolve to it; what that function cannot read is refused rather than judged as written. A name the callback leaves to sandbox-runtime's resolved-address guard, which resolves it once, for the dial, and refuses `deniedResolvedAddresses`, here the refused ranges less those opened on every port (subtracted with cidr-tools), as well as its own classes: loopback, link-local, cloud metadata and the host's addresses as they are at the lookup. An address and port in `allowedDomains` overrides both, so that list holds each exception that is a single address, and the host's addresses in each range opened, with the exception's port, less those in the guard's own classes, sorted by a guard with no allow list. The callback also refuses `localhost` and names under it, with any number of trailing dots: the guard, removing one dot, lets such a name resolve to any loopback address. Off, the deny list is `*`, with one reason, and there is no callback. sandbox-runtime's `NO_PROXY` also lists private and link-local ranges, so the Runner sets its own inside the sandbox, loopback alone: a private address then goes to the proxy, where it is refused with a reason or reached through an exception, rather than being dialled directly into nothing.

One change this needs is not released yet, so the Runner carries it as a pnpm patch to sandbox-runtime's published files until a release contains it: the reason in the body of a refused plain-HTTP request, from anthropics/sandbox-runtime#597.

A job's own loopback stays its own: on Linux its commands share one long-lived sandbox, pi-env's daemon, with a network namespace of its own, and `NO_PROXY` keeps `localhost` off the proxies, so a server one command starts is reached by the next. pi-web-access runs in a worker thread of the Runner's process, outside every sandbox, so the Runner holds it to the same settings through its `web-search.json`. Open, its requests go through sandbox-runtime's HTTP proxy, as jobs' commands do: `proxy` names the proxy with its token, `lockProxy` keeps a call from naming another, `ssrf.trustEnvProxy` lets the proxy judge a name by the address it dials, and the exceptions are `ssrf.allowRanges`, the ranges pi-web-access's own guard lets through. pi-web-access fetches `127.0.0.1`, `::1` and `169.254.169.254` without the proxy, so they are in `allowRanges` only as an exception naming the address alone, on every port: a range covering them leaves them out, as the proxy would, and so does a port, as `allowRanges` has none. For the same reason an operator's own `allowRanges` is refused while the network is open, and used as written under `none`, where every page fetch is refused anyway. GitHub cloning and the `gh` lookups of issues and pull requests, which reach GitHub past any proxy and past pi-web-access's checks, even for a URL with a scheme it does not fetch, are off in both modes, and the worker sees neither `NO_PROXY` nor `GCE_METADATA_HOST`, whose hosts pi-web-access would reach directly. With a proxy, pi-web-access sends every request through curl; `fetchContent.curl` names it for pages too, so that curl stops at the size limit instead of downloading a large file whole. Off, `fetch_content` is off, and `fetchContent.domainPolicy` allows only `invalid`, a name reserved never to exist, and denies it too, as the allow list also matches names under it, which refuses every page before it is looked up, including those pi-web-access would fetch to add to a search's results or for `source_check`, and those a fetching service would retrieve; pi-web-access then has no proxy, which would carry the search providers' requests too. The agent is told one sentence about its network, made from the same settings, so that it does not try what will be refused.

## Considered options

- A domain allow-list by default, opened per Runner: jobs' needs cannot be listed in advance, so every Runner would start broken for most work, and a name on the list says nothing about where it resolves.
- Leaving private ranges open, refusing only the host: the internal services a Runner's network reaches are the main thing a job could reach that the internet does not offer, and they often answer without authentication.
- Keeping the host's addresses refused whatever the exceptions: a range would open less than it says, unlike sandbox-runtime's own allow list, and an operator who means the host could not open it; one who does not writes a narrower range.
- Address ranges in sandbox-runtime's allow and deny lists, backported from anthropics/sandbox-runtime#807 as a patch: a range could take a port for names too, and the deny list would check IP destinations a second time, beside the callback. The backport was most of a 430-line patch on unreleased code that each upgrade rechecked, for cases an operator meets by opening a single address instead.
- Letting a range open every loopback, link-local and cloud metadata address it covers: shared space opened for Tailscale, or a unique-local range, would open a cloud's metadata service to jobs.
- Refusing only cloud metadata inside opened ranges, from a copy of sandbox-runtime's list: it leaves `169.254.169.254`, the address most clouds use, open under a link-local range, keeps typed addresses and names on different rules, and is a copy each upgrade rechecks.
- Resolving names in the ask callback: a name could resolve one way for the check and another for the dial. The guard resolves once, for the dial.
- Exceptions without ports: opening one service, such as a search provider on the Runner's host, would open every service at its address.
- pi-web-access's own guard against private addresses, given the exceptions, as its only check: it refuses less than the proxy, neither the host at a public address nor metadata endpoints in public space, and judges the address it resolved rather than the one it dials.
- Extensions in a sandboxed child process: sandbox-runtime's network policy is the process's, so under `none` a sandboxed pi-web-access could not reach the search providers either; a child takes about 50 MiB more than a worker thread (ADR 0038); the calls between host and extensions would need a new transport; and it would reverse ADR 0039, which trusts extensions as the Runner is trusted.
- Under `none`, a `fetchRouting.providers` list without `http`: pi-web-access still fetches the page itself first when its first provider is another, and `mode: "raw"` skips the list. Refusing `includeContent` in the Runner's guard instead would also drop the text providers return, which is search.
- Behind a corporate proxy, resolving a name in the callback before it goes on: the proxy resolves it again, possibly elsewhere, and hosts in such networks often cannot resolve outside names at all, so the callback would have to refuse those and break the internet, or allow them and let through any name an attacker controls. Connecting directly instead (`parentProxy.noProxy: "*"`) breaks the networks whose only way out is that proxy, and refusing to start without an operator's acknowledgement would refuse the same Runners without making them any safer.
- Adding the exceptions to the corporate proxy's `NO_PROXY`: an exception allows an address, while `NO_PROXY` chooses the route to it, and a service may be reachable only through that proxy, or meant to be reached through it; it would also route typed addresses directly while names resolving to them still went through the proxy.
- Telling the agent that names are unchecked behind a corporate proxy: the Runner does not know what that proxy refuses, so the sentence would not stop the agent trying what is refused, and it would point a misled agent at the gap.
- Waiting for #597's release: a plain-HTTP refusal would give a generic reason meanwhile, and the patch is small, on files that a release replaces.

## Consequences

The refusals go by address, so the Runner belongs on a machine without sensitive services: an address that reaches the host without being one of its own, such as a public address under 1:1 NAT, is not refused, and the host's addresses that ranges open are listed in `allowedDomains` as the Runner starts, so one the host gains later inside an opened range is open to typed addresses but refused to names until the Runner restarts; it fails closed, and keeping the list current would mean reconfiguring sandbox-runtime whenever an address changes. A Runner behind a corporate proxy, given in its own `HTTP_PROXY` or `HTTPS_PROXY` (or their lowercase forms), sends jobs' requests on to it by name, and that proxy resolves them, so sandbox-runtime's guard does not run and that proxy must refuse local and private addresses itself; the Runner says so as it starts, finding the proxy as sandbox-runtime does (`resolveParentProxy`), and names in the operator's `NO_PROXY` are dialled directly and checked. Whether an exception goes through that proxy is the operator's `NO_PROXY` too. IP destinations are judged by the callback, with no list of sandbox-runtime's behind it, so its tests ask it directly about each class, spellings, ports and exceptions. A refusal of a name that resolves into a refused range gives only the guard's class, such as a listed address, without the setting, and an `https://` refusal's reason is in the status phrase, which curl shows only with `-v`. Inside a job, `localhost`, `127.0.0.1` and `::1` are the job's own loopback, which `NO_PROXY` keeps off the proxies, so a host service an exception opens is reached at another of the host's addresses, as from a container. On macOS, jobs' commands have no loopback of their own, as Seatbelt refuses it. Each upgrade of sandbox-runtime rechecks the patch; the guard's list of cloud metadata endpoints, for one in public space that the Runner's ranges miss; the paths of `canonicalizeHost`, `splitDomainPatternPort`, `addRange`, `addressInSet`, `embeddedIPv4`, `isLoopbackName`, `createResolvedAddressGuard`, `localInterfaceAddresses` and `resolveParentProxy`, through which the Runner reads exceptions and destinations as sandbox-runtime reads them; how it spells the destination it gives the ask callback; and its `NO_PROXY`. Reconsider the patch when #597 is released or rejected; the Runner's `NO_PROXY` when sandbox-runtime's lists loopback alone (anthropics/sandbox-runtime#769); ranges in the allow and deny lists when #807 is released, which would let a range take a port and check IP destinations twice, keeping loopback, link-local and cloud metadata opened only by an entry naming the address; reading IP spellings in the callback when sandbox-runtime gives it the destination it matched; the corporate proxy's unchecked names when sandbox-runtime can resolve a name itself and send that proxy the address it checked; and the callback's refusal of `localhost` when sandbox-runtime checks `deniedResolvedAddresses` before it lets a loopback name resolve to loopback, or removes every trailing dot before matching. pi-web-access's Gemini Web, if turned on, and a YouTube video's frames and timestamps, which run `yt-dlp` and `ffmpeg` and follow `image.enabled` rather than `youtube.enabled`, do not use the proxy, and other extensions reach the network as the Runner does, so each upgrade of pi-web-access rechecks its routes, the addresses it fetches without the proxy, which the Runner copies, and the User-Agent copied from it for pages fetched through curl. Reconsider holding extensions by configuration rather than in a sandbox when a Runner runs extensions its operator has not vetted, when a second extension fetches URLs the job chooses, or when sandbox-runtime can give a process a policy of its own.
