# Job commands reach the internet, but not local or private addresses

A job's commands reach the public internet. Jobs install packages, call public APIs and fetch what their instructions point to, and a job that cannot do so works around it in ways that cost more and succeed less, or fails. What a Runner must keep from its jobs is what the internet does not already offer them: the Runner's own host, where its data, its credentials and services listening on loopback are, and the networks the host can reach that the internet cannot, where internal services often answer without authentication. So the default refuses destinations by address: `localhost` and the host's interface addresses as the Runner starts; loopback, link-local and cloud metadata addresses, including sandbox-runtime's list of metadata endpoints outside link-local space, such as Azure's `168.63.129.16`, which is in public space; private and shared address space; and the other rows of IANA's IPv4 and IPv6 special-purpose registries whose "Globally Reachable" is False, with multicast. Rows the registries mark globally reachable, or N/A, stay open. `::ffff:0:0/96` is not listed: sandbox-runtime reads that entry as every IPv4 address, and judges an IPv4-mapped destination by the IPv4 address it carries.

An operator opens ranges with `RUNNER_NETWORK_EXCEPTIONS`, for every job of the Runner: a Runner serves one organization, whose operator knows which internal services its jobs may use, and a setting per job would be a policy each caller could widen. An entry opens every port, or the one port it names, written as sandbox-runtime writes a destination (`10.0.0.0/8:8080`, `[fd00::5]:8080`), so that one service, such as a search provider the operator runs, can be opened without the rest of its host. A range opens IP destinations in it and names that resolve into it; a name alone opens nothing, as whoever controls a name's DNS decides where it points. A range opens exactly the addresses it covers, the host's own included, as sandbox-runtime's own refusals of the host and of loopback give way to an allowed range: an operator who opens a range holding a host address has opened the host there, and one who means less writes a narrower range. `/0` is refused, as it would open everything, the default's refusals included. `RUNNER_NETWORK=none` is for operators whose jobs must not reach the web: it refuses web access, any request to a destination the job picks, while search, a request to a provider the operator chose, which decides for itself what to contact, keeps working, with the page text a provider returns beside its results. A page a fetching service retrieves for a URL the job gave counts as web access, as the URL alone can carry data out. Both settings are enforced by the sandbox, so a Runner that would run jobs without one refuses to start with either.

sandbox-runtime enforces it, as it already confines the jobs (ADR 0027): every command reaches the network only through its proxies, which decide each destination from its process-wide configuration. The Runner's part is that configuration. The host's addresses and the refused ranges, the addresses less the exceptions (subtracted with cidr-tools), are its `deniedDomains`, each with a reason in `deniedDomainReasons` that names what is refused and the setting that opens it; the exceptions are its `allowedDomains`, with their ports; and an ask callback allows every other destination. The deny list cannot except a port, so it leaves out an exception's whole range, and the other ports of a range opened on one port are refused separately. The ask callback refuses an IP destination in such a range; sandbox-runtime gives it the destination as the client wrote it, so the callback reads the address with sandbox-runtime's own `canonicalizeHost`, imported from its `dist` as the package's main entry does not export it, which writes an IPv4-mapped address as its IPv4 address. A name is left to the resolved-address guard, to which those ranges are `deniedResolvedAddresses`, which an allowed address and port overrides. The callback also refuses `localhost` and names under it, with any number of trailing dots: the deny list matches with one dot removed, and the guard, removing another, lets such a name resolve to any loopback address the deny list leaves out, other ports of one opened on a port included. sandbox-runtime checks the deny list before the allow list and canonicalizes a destination first, so `127.1`, `2130706433` and `[::ffff:127.0.0.1]` are refused as `127.0.0.1` is. Its resolved-address guard holds names to the same lists, and its own refusals of loopback, link-local and the host's addresses give way only to a range in `allowedDomains`, which is why each exception is in both lists. Off, the configuration has no ask callback and every destination gets one reason, `allowlistDenyReason`.

Three changes this needs are not released yet, so the Runner carries them as a pnpm patch to sandbox-runtime's published files, each part dropped once a release contains it: anthropics/sandbox-runtime#807, IP literals and CIDR ranges in `allowedDomains` and `deniedDomains`, fed to the resolved-address guard; anthropics/sandbox-runtime#769, `NO_PROXY` listing loopback only, so a private address goes to the proxy, where it is refused with a reason or reached through an exception, rather than dialled directly into nothing; and anthropics/sandbox-runtime#597, the reason in the body of a refused plain-HTTP request, and `allowlistDenyReason`.

A job's own loopback stays its own: on Linux its commands share one long-lived sandbox, pi-env's daemon, with a network namespace of its own, and `NO_PROXY` keeps `localhost` off the proxies, so a server one command starts is reached by the next. pi-web-access runs in a worker thread of the Runner's process, outside every sandbox, so the Runner holds it to the same settings through its `web-search.json`. Open, its requests go through sandbox-runtime's HTTP proxy, as jobs' commands do: `proxy` names the proxy with its token, `lockProxy` keeps a call from naming another, `ssrf.trustEnvProxy` lets the proxy judge a name by the address it dials, and the exceptions are `ssrf.allowRanges`, the ranges pi-web-access's own guard lets through. `allowRanges` has no ports, which the proxy enforces, so a range opened on one port leaves out `127.0.0.1`, `::1` and `169.254.169.254`, which pi-web-access fetches without the proxy. For the same reason an operator's own `allowRanges` is refused while the network is open, and used as written under `none`, where every page fetch is refused anyway. GitHub cloning and the `gh` lookups of issues and pull requests, which reach GitHub past any proxy and past pi-web-access's checks, even for a URL with a scheme it does not fetch, are off in both modes, and the worker sees neither `NO_PROXY` nor `GCE_METADATA_HOST`, whose hosts pi-web-access would reach directly. With a proxy, pi-web-access sends every request through curl; `fetchContent.curl` names it for pages too, so that curl stops at the size limit instead of downloading a large file whole. Off, `fetch_content` is off, and `fetchContent.domainPolicy.allow` lists only `invalid`, a name reserved never to exist, which refuses every page before it is looked up, including those pi-web-access would fetch to add to a search's results or for `source_check`, and those a fetching service would retrieve; pi-web-access then has no proxy, which would carry the search providers' requests too. The agent is told one sentence about its network, made from the same settings, so that it does not try what will be refused.

## Considered options

- A domain allow-list by default, opened per Runner: jobs' needs cannot be listed in advance, so every Runner would start broken for most work, and a name on the list says nothing about where it resolves.
- Leaving private ranges open, refusing only the host: the internal services a Runner's network reaches are the main thing a job could reach that the internet does not offer, and they often answer without authentication.
- Keeping the host's addresses refused whatever the exceptions: a range would open less than it says, unlike sandbox-runtime's own allow list, and an operator who means the host could not open it; one who does not writes a narrower range.
- Our own address checks in the ask callback, without the patch: the callback gets the destination as the client spelled it, so the Runner would canonicalize IP spellings and resolve names itself, beside the code that dials, and a name could resolve one way for the check and another for the dial. The patch puts ranges where sandbox-runtime already canonicalizes and resolves. The callback reads destinations, with sandbox-runtime's own function, only for what the lists cannot say, the other ports of an address opened on one port and `localhost` with trailing dots, and never resolves a name.
- Exceptions without ports: opening one service, such as a search provider on the Runner's host, would open every service at its address.
- pi-web-access's own guard against private addresses, given the exceptions, as its only check: it refuses less than the proxy, neither the host at a public address nor metadata endpoints in public space, and judges the address it resolved rather than the one it dials.
- Extensions in a sandboxed child process: sandbox-runtime's network policy is the process's, so under `none` a sandboxed pi-web-access could not reach the search providers either; a child takes about 50 MiB more than a worker thread (ADR 0038); the calls between host and extensions would need a new transport; and it would reverse ADR 0039, which trusts extensions as the Runner is trusted.
- Under `none`, a `fetchRouting.providers` list without `http`: pi-web-access still fetches the page itself first when its first provider is another, and `mode: "raw"` skips the list. Refusing `includeContent` in the Runner's guard instead would also drop the text providers return, which is search.
- Waiting for upstream releases: jobs would keep no network meanwhile, and the patch is small, on files that a release replaces.

## Consequences

The refusals go by address, so the Runner belongs on a machine without sensitive services: an address that reaches the host without being one of its own, such as a public address under 1:1 NAT, is not refused, and the host's addresses are read once, as the Runner starts. A Runner behind a corporate proxy, given in its own `HTTP_PROXY` or `HTTPS_PROXY`, sends jobs' requests on to it, and sandbox-runtime then skips the address checks on names, so that proxy must refuse local and private addresses itself, and names reach every port of a range opened on one. A refusal of a name that resolves into a refused range says only that it resolved to a deny-listed address, without the class or the setting, and an `https://` refusal's reason is in the status phrase, which curl shows only with `-v`. Inside a job, `localhost`, `127.0.0.1` and `::1` are the job's own loopback, which `NO_PROXY` keeps off the proxies, so a host service an exception opens is reached at another of the host's addresses, as from a container. On macOS, jobs' commands have no loopback of their own, as Seatbelt refuses it. Each upgrade of sandbox-runtime rechecks the patch, which also exports the resolved-address guard's list of cloud metadata endpoints so that the Runner refuses the same ones as literals, the paths of `canonicalizeHost`, `splitDomainPatternPort`, `addRange`, `addressInSet` and `isLoopbackName`, through which the Runner reads exceptions and destinations as sandbox-runtime reads them, and how it spells the destination it gives the ask callback. Reconsider the patch when #807, #769 or #597 is released or rejected, reading IP spellings in the callback when sandbox-runtime gives it the destination it matched, or lets an allowed port override a denied range, and the callback's refusal of `localhost` when sandbox-runtime checks `deniedResolvedAddresses` before it lets a loopback name resolve to loopback, or removes every trailing dot before matching. pi-web-access's Gemini Web, if turned on, and a YouTube video's frames and timestamps, which run `yt-dlp` and `ffmpeg` and follow `image.enabled` rather than `youtube.enabled`, do not use the proxy, and other extensions reach the network as the Runner does, so each upgrade of pi-web-access rechecks its routes, the addresses it fetches without the proxy, which the Runner copies, and the User-Agent copied from it for pages fetched through curl. Reconsider holding extensions by configuration rather than in a sandbox when a Runner runs extensions its operator has not vetted, when a second extension fetches URLs the job chooses, or when sandbox-runtime can give a process a policy of its own.
