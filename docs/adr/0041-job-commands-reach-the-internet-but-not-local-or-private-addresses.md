# Job commands reach the internet, but not local or private addresses

A job's commands reach the public internet. Jobs install packages, call public APIs and fetch what their instructions point to, and a job that cannot do so works around it in ways that cost more and succeed less, or fails. What a Runner must keep from its jobs is what the internet does not already offer them: the Runner's own host, where its data, its credentials and services listening on loopback are, and the networks the host can reach that the internet cannot, where internal services often answer without authentication. So the default refuses destinations by address: `localhost` and the host's interface addresses as the Runner starts; loopback, link-local and cloud metadata addresses, including sandbox-runtime's list of metadata endpoints outside link-local space, such as Azure's `168.63.129.16`, which is in public space; private and shared address space; and the other rows of IANA's IPv4 and IPv6 special-purpose registries whose "Globally Reachable" is False, with multicast. Rows the registries mark globally reachable, or N/A, stay open. `::ffff:0:0/96` is not listed: sandbox-runtime reads that entry as every IPv4 address, and judges an IPv4-mapped destination by the IPv4 address it carries.

An operator opens ranges with `RUNNER_NETWORK_EXCEPTIONS`, for every job of the Runner and every port: a Runner serves one organization, whose operator knows which internal services its jobs may use, and a setting per job would be a policy each caller could widen. A range opens IP destinations in it and names that resolve into it; a name alone opens nothing, as whoever controls a name's DNS decides where it points. The host's own addresses and `localhost` stay refused whatever the exceptions. `RUNNER_NETWORK=none` turns the network off, for operators whose jobs must reach nothing.

sandbox-runtime enforces it, as it already confines the jobs (ADR 0027): every command reaches the network only through its proxies, which decide each destination from its process-wide configuration. The Runner's part is that configuration. The refused ranges, less the exceptions (subtracted with cidr-tools), and then `localhost` and the host's addresses, are its `deniedDomains`, each with a reason in `deniedDomainReasons` that names what is refused and the setting that opens it; the exceptions are its `allowedDomains`; and an ask callback allows every other destination. sandbox-runtime checks the deny list before the allow list and canonicalizes a destination first, so `127.1`, `2130706433` and `[::ffff:127.0.0.1]` are refused as `127.0.0.1` is. Its resolved-address guard holds names to the same lists, and its own refusals of loopback, link-local and the host's addresses give way only to a range in `allowedDomains`, which is why each exception is in both lists. Off, the configuration has no ask callback and every destination gets one reason, `allowlistDenyReason`.

Three changes this needs are not released yet, so the Runner carries them as a pnpm patch to sandbox-runtime's published files, each part dropped once a release contains it: anthropics/sandbox-runtime#807, IP literals and CIDR ranges in `allowedDomains` and `deniedDomains`, fed to the resolved-address guard; anthropics/sandbox-runtime#769, `NO_PROXY` listing loopback only, so a private address goes to the proxy, where it is refused with a reason or reached through an exception, rather than dialled directly into nothing; and anthropics/sandbox-runtime#597, the reason in the body of a refused plain-HTTP request, and `allowlistDenyReason`.

A job's own loopback stays its own: on Linux its commands share one long-lived sandbox, pi-env's daemon, with a network namespace of its own, and `NO_PROXY` keeps `localhost` off the proxies, so a server one command starts is reached by the next. pi-web-access's requests leave from the Runner's process, outside every sandbox, so the Runner applies the same settings to its `web-search.json`: off, `fetch_content` is off; open, the exceptions join `ssrf.allowRanges`, the ranges its own guard against private addresses lets through. The agent is told one sentence about its network, made from the same settings, so that it does not try what will be refused.

## Considered options

- A domain allow-list by default, opened per Runner: jobs' needs cannot be listed in advance, so every Runner would start broken for most work, and a name on the list says nothing about where it resolves.
- Leaving private ranges open, refusing only the host: the internal services a Runner's network reaches are the main thing a job could reach that the internet does not offer, and they often answer without authentication.
- Our own address checks in the ask callback, without the patch: the callback gets the destination as the client spelled it, so the Runner would canonicalize IP spellings and resolve names itself, beside the code that dials, and a name could resolve one way for the check and another for the dial. The patch puts ranges where sandbox-runtime already canonicalizes and resolves.
- Waiting for upstream releases: jobs would keep no network meanwhile, and the patch is small, on files that a release replaces.

## Consequences

The refusals go by address, so the Runner belongs on a machine without sensitive services: an address that reaches the host without being one of its own, such as a public address under 1:1 NAT, is not refused, and the host's addresses are read once, as the Runner starts. A Runner behind a corporate proxy, given in its own `HTTP_PROXY` or `HTTPS_PROXY`, sends jobs' requests on to it, and sandbox-runtime then skips the address checks on names, so that proxy must refuse local and private addresses itself. A refusal of a name that resolves into a refused range says only that it resolved to a deny-listed address, without the class or the setting, and an `https://` refusal's reason is in the status phrase, which curl shows only with `-v`. On macOS, jobs' commands have no loopback of their own, as Seatbelt refuses it. Each upgrade of sandbox-runtime rechecks the patch. Reconsider the patch when #807, #769 or #597 is released or rejected, and the refusal of the host's addresses when a deployment needs jobs to use a service on the Runner's own host.
