# Job commands reach the internet, but not local or private addresses

A job's commands reach the public internet. Jobs install packages, call public APIs and fetch what their instructions point to, and a job that cannot do so works around it in ways that cost more and succeed less, or fails. What a Runner must keep from its jobs is what the internet does not already offer them: the Runner's own host, where its data, its credentials and services listening on loopback are, and the networks the host can reach that the internet cannot, where internal services often answer without authentication. So the default refuses destinations by address: `localhost` and the host's interface addresses as the Runner starts; loopback, link-local and cloud metadata addresses, including Azure's `168.63.129.16`, which is in public space, the other endpoints being in refused ranges; private and shared address space; and the other rows of IANA's IPv4 and IPv6 special-purpose registries whose "Globally Reachable" is False, with multicast. Rows the registries mark globally reachable, or N/A, stay open. `::ffff:0:0/96` is not listed: a `BlockList` reads that range as every IPv4 address, and an IPv4-mapped destination is judged by the IPv4 address it carries.

An operator opens ranges with `RUNNER_NETWORK_EXCEPTIONS`, for every job of the Runner: a Runner serves one organization, whose operator knows which internal services its jobs may use, and a setting per job would be a policy each caller could widen. An entry opens every port, or the one port it names, written as sandbox-runtime writes a destination (`10.0.0.0/8:8080`, `[fd00::5]:8080`), so that one service, such as a search provider the operator runs, can be opened without the rest of its host. A range opens IP destinations in it and, with the limits below, names that resolve into it; a name alone opens nothing, as whoever controls a name's DNS decides where it points. A range opens exactly the addresses it covers, the host's own included: an operator who opens a range holding a host address has opened the host there, and one who means less writes a narrower range. `/0` is refused, as it would open everything, the default's refusals included. `RUNNER_NETWORK=none` is for operators whose jobs must not reach the web: it refuses web access, any request to a destination the job picks, while search, a request to a provider the operator chose, which decides for itself what to contact, keeps working, with the page text a provider returns beside its results. A page a fetching service retrieves for a URL the job gave counts as web access, as the URL alone can carry data out. Both settings are enforced by the sandbox, so a Runner that would run jobs without one refuses to start with either.

sandbox-runtime enforces it, as it already confines the jobs (ADR 0027): every command reaches the network only through its proxies, which decide each destination from its process-wide configuration. The Runner's part is that configuration and its ask callback. Open, the deny list is empty and the allow list holds only single addresses, so nearly every destination reaches the callback. The callback judges an IP destination itself: it refuses one among the host's addresses or in a refused range unless an exception covers it on that port, with a reason that names what is refused and the setting that opens it. sandbox-runtime gives the callback the destination as the client wrote it, so the callback reads it with sandbox-runtime's own `canonicalizeHost`, imported from its `dist` as the package's main entry does not export it, which is how `127.1`, `2130706433` and `[::ffff:127.0.0.1]` are refused as `127.0.0.1` is; what that function cannot read is refused rather than judged as written. A name the callback leaves to sandbox-runtime's resolved-address guard, which resolves it once, for the dial, and refuses `deniedResolvedAddresses`, here the host's addresses and the refused ranges less those opened on every port (subtracted with cidr-tools), as well as its own classes: loopback, link-local, cloud metadata and the host's addresses. An address and port in `allowedDomains` overrides both, so that list holds each exception that is a single address, and the host's addresses in each range opened, with the exception's port. The callback also refuses `localhost` and names under it, with any number of trailing dots: the guard, removing one dot, lets such a name resolve to any loopback address. Off, the deny list is `*`, with one reason, and there is no callback. sandbox-runtime's `NO_PROXY` also lists private and link-local ranges, so the Runner sets its own inside the sandbox, loopback alone: a private address then goes to the proxy, where it is refused with a reason or reached through an exception, rather than being dialled directly into nothing.

One change this needs is not released yet, so the Runner carries it as a pnpm patch to sandbox-runtime's published files until a release contains it: the reason in the body of a refused plain-HTTP request, from anthropics/sandbox-runtime#597.

A job's own loopback stays its own: on Linux its commands share one long-lived sandbox, pi-env's daemon, with a network namespace of its own, and `NO_PROXY` keeps `localhost` off the proxies, so a server one command starts is reached by the next. pi-web-access runs in a worker thread of the Runner's process, outside every sandbox, so the Runner holds it to the same settings through its `web-search.json`. Open, its requests go through sandbox-runtime's HTTP proxy, as jobs' commands do: `proxy` names the proxy with its token, `lockProxy` keeps a call from naming another, `ssrf.trustEnvProxy` lets the proxy judge a name by the address it dials, and the exceptions are `ssrf.allowRanges`, the ranges pi-web-access's own guard lets through. `allowRanges` has no ports, which the proxy enforces, so a range opened on one port leaves out `127.0.0.1`, `::1` and `169.254.169.254`, which pi-web-access fetches without the proxy. For the same reason an operator's own `allowRanges` is refused while the network is open, and used as written under `none`, where every page fetch is refused anyway. GitHub cloning and the `gh` lookups of issues and pull requests, which reach GitHub past any proxy and past pi-web-access's checks, even for a URL with a scheme it does not fetch, are off in both modes, and the worker sees neither `NO_PROXY` nor `GCE_METADATA_HOST`, whose hosts pi-web-access would reach directly. With a proxy, pi-web-access sends every request through curl; `fetchContent.curl` names it for pages too, so that curl stops at the size limit instead of downloading a large file whole. Off, `fetch_content` is off, and `fetchContent.domainPolicy.allow` lists only `invalid`, a name reserved never to exist, which refuses every page before it is looked up, including those pi-web-access would fetch to add to a search's results or for `source_check`, and those a fetching service would retrieve; pi-web-access then has no proxy, which would carry the search providers' requests too. The agent is told one sentence about its network, made from the same settings, so that it does not try what will be refused.

## Considered options

- A domain allow-list by default, opened per Runner: jobs' needs cannot be listed in advance, so every Runner would start broken for most work, and a name on the list says nothing about where it resolves.
- Leaving private ranges open, refusing only the host: the internal services a Runner's network reaches are the main thing a job could reach that the internet does not offer, and they often answer without authentication.
- Keeping the host's addresses refused whatever the exceptions: a range would open less than it says, unlike sandbox-runtime's own allow list, and an operator who means the host could not open it; one who does not writes a narrower range.
- Address ranges in sandbox-runtime's allow and deny lists, backported from anthropics/sandbox-runtime#807 as a patch: names would reach a range opened on one port, on that port, and a loopback, link-local or metadata address in an opened range, and the deny list would check IP destinations a second time, beside the callback. The backport was most of a 430-line patch on unreleased code that each upgrade rechecked, for cases an operator meets by opening a single address instead.
- Resolving names in the ask callback: a name could resolve one way for the check and another for the dial. The guard resolves once, for the dial.
- Exceptions without ports: opening one service, such as a search provider on the Runner's host, would open every service at its address.
- pi-web-access's own guard against private addresses, given the exceptions, as its only check: it refuses less than the proxy, neither the host at a public address nor metadata endpoints in public space, and judges the address it resolved rather than the one it dials.
- Extensions in a sandboxed child process: sandbox-runtime's network policy is the process's, so under `none` a sandboxed pi-web-access could not reach the search providers either; a child takes about 50 MiB more than a worker thread (ADR 0038); the calls between host and extensions would need a new transport; and it would reverse ADR 0039, which trusts extensions as the Runner is trusted.
- Under `none`, a `fetchRouting.providers` list without `http`: pi-web-access still fetches the page itself first when its first provider is another, and `mode: "raw"` skips the list. Refusing `includeContent` in the Runner's guard instead would also drop the text providers return, which is search.
- Waiting for #597's release: a plain-HTTP refusal would give a generic reason meanwhile, and the patch is small, on files that a release replaces.

## Consequences

The refusals go by address, so the Runner belongs on a machine without sensitive services: an address that reaches the host without being one of its own, such as a public address under 1:1 NAT, is not refused, and the host's addresses are read once, as the Runner starts. A Runner behind a corporate proxy, given in its own `HTTP_PROXY` or `HTTPS_PROXY`, sends jobs' requests on to it, and sandbox-runtime then skips the address checks on names, so that proxy must refuse local and private addresses itself. A name that resolves into a range opened on one port is refused even on that port, and one that resolves to a loopback, link-local or cloud metadata address in an opened range is refused unless that address is opened alone; the operator opens the address itself. IP destinations are checked once, by the callback, with no second list behind it, so its tests ask it directly about each class, spellings, ports and exceptions. A refusal of a name that resolves into a refused range gives only the guard's class, such as a listed address, without the setting, and an `https://` refusal's reason is in the status phrase, which curl shows only with `-v`. Inside a job, `localhost`, `127.0.0.1` and `::1` are the job's own loopback, which `NO_PROXY` keeps off the proxies, so a host service an exception opens is reached at another of the host's addresses, as from a container. On macOS, jobs' commands have no loopback of their own, as Seatbelt refuses it. Each upgrade of sandbox-runtime rechecks the patch; the guard's list of cloud metadata endpoints, for one in public space that the Runner's ranges miss; the paths of `canonicalizeHost`, `splitDomainPatternPort`, `addRange`, `addressInSet` and `isLoopbackName`, through which the Runner reads exceptions and destinations as sandbox-runtime reads them; how it spells the destination it gives the ask callback; and its `NO_PROXY`. Reconsider the patch when #597 is released or rejected; the Runner's `NO_PROXY` when sandbox-runtime's lists loopback alone (anthropics/sandbox-runtime#769); ranges in the allow and deny lists when #807 is released, which would let names reach a range opened on one port and check IP destinations twice; reading IP spellings in the callback when sandbox-runtime gives it the destination it matched; and the callback's refusal of `localhost` when sandbox-runtime checks `deniedResolvedAddresses` before it lets a loopback name resolve to loopback, or removes every trailing dot before matching. pi-web-access's Gemini Web, if turned on, and a YouTube video's frames and timestamps, which run `yt-dlp` and `ffmpeg` and follow `image.enabled` rather than `youtube.enabled`, do not use the proxy, and other extensions reach the network as the Runner does, so each upgrade of pi-web-access rechecks its routes, the addresses it fetches without the proxy, which the Runner copies, and the User-Agent copied from it for pages fetched through curl. Reconsider holding extensions by configuration rather than in a sandbox when a Runner runs extensions its operator has not vetted, when a second extension fetches URLs the job chooses, or when sandbox-runtime can give a process a policy of its own.
