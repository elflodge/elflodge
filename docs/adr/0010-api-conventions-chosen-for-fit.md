# API conventions are chosen for fit, in camelCase

The API uses camelCase for field names and for string values (`customId`, `outputContract`, `runTimedOut`), with lowercase, plural, hyphenated URL paths (`/jobs/:id`, `/api-keys`). Cloudflare Workflows, the platform service closest to ours, does the same in its JavaScript API, including state values such as `waitingForPause`. Several of our surfaces are camelCase whatever we choose (JavaScript callers, the JSON Schema keywords inside output contracts, data from Pi), so camelCase is the only casing that can be the same everywhere. Agent tool names are the exception: they follow the snake_case convention models are trained on (`submit_output`).

Patterns are chosen for how well they fit what we need, not by the project they come from: a less common design that works better wins over the most familiar one. Names inside our code and our domain terms are our own, chosen for clarity.

A single resource is returned bare. A list is returned in pages, each a page object whose items are named for what they hold.

A job's events can be read oldest first to follow a run, or newest first to open its recent history. Ascending order (`order=asc`) is the default to preserve the released behaviour. In either order, `after` is exclusive. Use the last ID on a page to continue in that order, or 0 to start at its first event. For example, if a descending page holds IDs 98 and 93, read older events with `order=desc&after=93` and follow new ones with `after=98`. Redis Streams' `XREAD`, CouchDB's changes feed and the browser's `Last-Event-ID` likewise read on from a position the reader keeps. OpenAI's conversation items list pairs `order` with an `after` item ID. AWS Step Functions lets callers request newest-first execution history with `reverseOrder` on the same read. [OpenAI List items](https://developers.openai.com/api/reference/resources/conversations/subresources/items/methods/list) · [AWS GetExecutionHistory](https://docs.aws.amazon.com/step-functions/latest/apireference/API_GetExecutionHistory.html)

Each page returns up to `limit` events (1–100). Its Events have a 1 MiB budget, with the first eligible event included even if it alone exceeds that budget. When `hasMore` is true, more events are already stored in that order and the caller asks again at once. A descending page with `hasMore: false` finishes the walk back through history. Newer events may have arrived during that walk. A follower reads forward from the newest ID seen (or 0 if the first page was empty), polling every few seconds once caught up. An ascending page with a final `status` and `hasMore: false` reaches the end of that run. A caller waiting for the run can stop there. A member watching the job can keep following the same cursor to see a resume.

A list of jobs is read newest first. `after` takes the ID of the last job the caller has, and the page holds the jobs created before it, `limit` of them (1 to 100, 50 by default), saying `hasMore` when there are more, as Stripe's `starting_after` takes an object's ID. Job IDs are UUIDv7s, ordered by when they were made, so the ID alone orders the list, and a page stays correct when the job it starts after is deleted or new jobs come meanwhile; those show on a new first page. Filters, such as a label or a status, narrow the list without changing its order.

Every input of the API (`apiContract`) is checked strictly, in its body and in a read's query string: a parameter the call does not define, such as one renamed or misspelled, is refused with 400 naming it and its path, while the Runner's own calls follow ADR 0026. Ignoring it would run the request as if it were absent, such as a job without the files its caller meant to give it, or a list without the filter its caller misspelled, answering with every job. Refusing it also keeps the name free for a parameter added later, which an old caller's stray one would otherwise collide with. Microsoft's Azure REST API guidelines fail a request with any JSON field or list parameter the service does not support, Zalando's guidelines recommend answering 400 to unknown input fields in the payload or URL, the Anthropic and OpenAI APIs refuse unknown fields in a request body, and Anthropic's Compliance API refuses a query parameter its endpoint does not define, rather than ignoring it. Answers are not checked that way, so the hub can add fields to them without breaking a caller that validates them, and the OpenAPI document leaves `additionalProperties: false` out of them; nor are the upload's headers, which carry far more than the API reads.

A stray query parameter on a write is ignored, not refused: oRPC's compact input passes every read's query string to its schema, but a write's only for the upload (`PUT /blobs/{digest}`), whose outer object drops it. A body that is not an object, on a call with path parameters, is taken as no body, so an array sent to `POST /jobs/{id}/resume`, whose fields are all optional, resumes the job with its defaults. The hub refuses unknown fields in every body, and the OpenAPI document says so with `additionalProperties: false`.

## Considered options

snake_case field names, as in Cloudflare's account-level REST API, Wrangler configuration, and the OpenAI and Anthropic APIs, would look familiar to some callers, but the same job would then be snake_case over HTTP and camelCase in JavaScript, with camelCase schema keywords nested inside snake_case fields. Our callers send jobs, not model requests, so they gain little from matching the model APIs.

Keeping only the ascending events read would take at least 51 sequential requests to open the latest event of a 5,001-event job. IDs can have gaps, so the caller cannot calculate a starting ID. A second cursor like Stripe's `ending_before` would need a sentinel or another input to start at the newest event, and a rule for requests supplying both cursors. It would also make `after` mean a greater ID here while it means an older job in `jobs.list`. A separate reverse-history route like Temporal's would duplicate the procedure, permission, page and limits. Reconsider the events read if live following moves to a pushed stream or callers need to jump to a time or filter by event kind. Reconsider storing one report per row if reading a few recent events routinely requires parsing megabytes. [Stripe pagination](https://docs.stripe.com/api/pagination) · [Temporal history procedures](https://github.com/temporalio/api/blob/master/temporal/api/workflowservice/v1/service.proto)

An opaque cursor like Google's AIP-158 `page_token` for jobs, or separate forward and backward tokens like CloudWatch Logs' for events, would encode only the ID the caller already has. A job list would also need a rule for a request whose filters differ from those the cursor was minted with. A later sort order, such as by when a job ended, would need a position the ID alone cannot give. A cursor for that order would then come beside `after`. [CloudWatch Logs GetLogEvents](https://docs.aws.amazon.com/AmazonCloudWatchLogs/latest/APIReference/API_GetLogEvents.html)

Using `inputStructure: "detailed"` on every write would make the query string available to validate. It would also change the typed input of every write but the upload, which already uses it, to separate `{ params, query, body }` parts, changing both handlers and clients. Reconsider this if a write gains query parameters.

Unknown parameters could be dropped silently, as Zod's `z.object` does by default, so a hub would accept a request from a caller newer than itself. But a misspelled or renamed parameter would then run the request as if it were absent, and the caller would learn of it only from a wrong result, if at all. Accepting them with a warning, as Kubernetes's `fieldValidation=Warn` does, still runs that request and tells only a caller that reads warnings, which a program submitting jobs rarely does. Refusing them should be reconsidered if callers commonly run against hubs older than themselves, which would then refuse the parameters added since; a caller could leave out what its hub does not know, or a request could ask for unknown parameters to be ignored.
