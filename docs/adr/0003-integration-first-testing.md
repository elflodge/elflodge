# Integration-first testing on real runtimes, with the dashboard's pages against a stand-in for the hub

Tests exercise the public API as outside callers: Vitest runs in Node and starts the hub twice over, as a Worker from its Wrangler config in real workerd with Wrangler's `createTestHarness()` and as a Node process as its Docker image runs it, and runs the same suite against each, alongside a real Postgres from Testcontainers, and starts the Node runner in the test process, dialling the hub's URL over a real WebSocket as on a host, or in a process of its own where a test kills it outright, since a test cannot kill its own process. Unit tests are written only for dense logic that is awkward to reach through the API, such as pure functions or timing that only Effect's test clock can reach without real waits, and for contracts beneath it that their owner defines a suite for: each Execution environment runs pi-durable's environment conformance cases next to its code, as pi-durable's own environments do, and tests what pi-durable's tools rely on beyond those cases, since a job reaches them only through a model's tool calls. Pi and the execution environments are never mocked; pi-ai's faux model stands in for the LLM so runs stay deterministic and free.

The dashboard is tested in two places. What a page does with the hub's answers, such as its words, the requests it sends, where focus goes, what a read does to an open dialog and its deadlines, is tested in the dashboard's package: Playwright, under Vitest like the rest, drives the production build in Chromium, each test in a browser context of its own, against a stand-in for the hub at the HTTP boundary. The stand-in implements the API's contract as one oRPC router, whose procedures answer what the test arranged, and MSW serves it through the hub's API handler, so the hub's routing picks the procedure, a test arranges a procedure's result, one of its declared refusals or a lost answer, the contract checks the request and the made-up answer, and a refusal reaches the page as the hub writes it; Better Auth's routes are arranged the same way, typed from its client, and answer only the methods their endpoints declare. The one difference from the hub is that an upload is held to a JSON body's limit, where the hub gives uploads a handler that takes a file's size. A request no test arranged fails the test, except one the hub's handler refuses before the procedure runs, such as a call whose input the contract refuses, which the hub's refusal answers. The page's clock stands still until a test moves it, so a poll or a deadline costs no wait. Where what a test claims is what the hub accepted, stored or refused, such as a Runner registering with the key the dashboard showed, a submission with its uploads, an invitation accepted or an owner leaving, a journey drives the page against a real hub, on the Node hub only: a page takes two things from a hub, the build, which is the same on both, and the API's answers, and the rest of the suite checks on each hub how it serves the one and gives the other.

Before, every page test ran against a real hub, Postgres and often a Runner, and those tests were most of the suite's time: arranging one answer cost seconds, a poll was waited for, and a race between a read and a press still had to be staged by intercepting requests, since no hub produces it on demand. Vitest's Browser Mode would test the source without a build, and was tried: in Vitest 5.1 one browser context serves the whole run, so pointer position, emulation and routes carried from one file to the next and a real tap failed intermittently; Solid's production runtime could be had only by setting `NODE_ENV` inside the config, which no documentation names; and mounting needed the root document replaced through an alias, since TanStack Start documents no way to mount an app in a test. Route fixtures written by hand answered 200 to a request the hub refuses, `GET /runners?unexpected=1`. jsdom shows neither focus nor `inert` nor layout. Splitting the suite across more jobs with Vitest's `--shard` shortens the wait and keeps the cost. The price of driving the build is that an edit is built before it is tested. What the stand-in cannot vouch for is what the contract does not state, such as which member may do what, or the order of a list: the journeys and the hub's own tests carry that. Reconsider Browser Mode when Vitest gives each file a browser context of its own and TanStack Start documents mounting in a browser test. Reconsider running the journeys on one hub when a page depends on something the hubs do differently that no test of the API shows.

Container tests (real programs through the container backend) live in the same suite but are tagged and skipped by default, because they need Docker and an image build: the default `vp test` run excludes them, a separate run includes them, and CI runs them with the other checks when a pull request enters the merge queue.
