# Integration-first testing on real runtimes, with the dashboard's pages against a stand-in for the hub

Tests exercise the public API as outside callers: Vitest runs in Node and starts the hub twice over, as a Worker from its Wrangler config in real workerd with Wrangler's `createTestHarness()` and as a Node process as its Docker image runs it, and runs the same suite against each, alongside a real Postgres from Testcontainers, and starts the Node runner in the test process, dialling the hub's URL over a real WebSocket as on a host, or in a process of its own where a test kills it outright, since a test cannot kill its own process. Unit tests are written only for dense logic that is awkward to reach through the API, such as pure functions or timing that only Effect's test clock can reach without real waits, and for contracts beneath it that their owner defines a suite for: each Execution environment runs pi-durable's environment conformance cases next to its code, as pi-durable's own environments do, and tests what pi-durable's tools rely on beyond those cases, since a job reaches them only through a model's tool calls. Pi and the execution environments are never mocked; pi-ai's faux model stands in for the LLM so runs stay deterministic and free.

The dashboard is tested in two places. What a page does with the hub's answers, such as its words, the requests it sends, where focus goes, what a read does to an open dialog and its deadlines, is tested in the dashboard's package with Vitest's Browser Mode: each test file runs in Chromium through Playwright and mounts the dashboard's own router, with its routes and its Query client, from source, against a stand-in for the hub that answers the page's `fetch`. The stand-in implements the API's contract as one oRPC router, whose procedures answer what the test arranged, and the hub's API handler serves it, so the hub's routing picks the procedure, a test arranges a procedure's result, one of its declared refusals or a lost answer, the contract checks the request and the made-up answer, and a refusal reaches the page as the hub writes it; Better Auth's routes are arranged the same way, typed from its client, and answer only the methods their endpoints declare. The one difference from the hub is that an upload is held to a JSON body's limit, where the hub gives uploads a handler that takes a file's size. These fail the test, which names them: a request no test arranged, a WebSocket among them, an arranged answer that throws, other than a procedure's declared refusal, or that the contract refuses, and a request sent after the test has ended. A request the hub's handler refuses before the procedure runs, such as a call whose input the contract refuses, needs no arrangement, as the hub's refusal answers it. The tests run on Vitest's fake timers, which Vitest moves on while an action or an assertion waits, so a poll or a deadline costs no wait and the page's own timers run as they do for a member; a test of a deadline reads the clock when the request arrives and checks without retrying, since a retry moves the clock. A file is the unit of isolation, as it is Vitest's: a document shows one member (ADR 0046), so tests of different members go in different files, and each test's cleanup disposes of its mount. Where what a test claims is what the hub accepted, stored or refused, such as a Runner registering with the key the dashboard showed, a submission with its uploads, an invitation accepted or an owner leaving, or needs the document replaced or a second tab, such as a session ended elsewhere or another member signing in beside it, a journey drives the page against a real hub, on the Node hub only: a page takes two things from a hub, the build, which is the same on both, and the API's answers, and the rest of the suite checks on each hub how it serves the one and gives the other. The journeys are the tests in `apps/hub/tests/journeys`: the package and that directory, not a pattern in a file's name, put a test on one side of the boundary or the other.

Before, every page test ran against a real hub, Postgres and often a Runner, and those tests were most of the suite's time: arranging one answer cost seconds, a poll was waited for, and a race between a read and a press still had to be staged by intercepting requests, since no hub produces it on demand. Then the page tests drove the production build from outside, Playwright under Vitest, each test in a browser context of its own, against the same stand-in through a Playwright route, with the page's clock paused until a test moved it. The paused clock hid what members meet: no timer of the page ran unless a test stepped it, so focus lost after Apply on the jobs list, a page not yet inert after a dialog opened and an announcement never written all passed. And each edit was built before it was tested, about 4.5 seconds that no option of Vite or TanStack Start shortens, where Browser Mode reaches a result in watch mode in under 4. Browser Mode's price is that the page tests run the source on Solid's development runtime, whose diagnostics they keep, not the bundle the hub serves, and that the app's root document is replaced through an alias, since Solid cannot create a document inside one that exists (solidjs/solid#3259) and TanStack Start documents no way to mount an app in a test; the journeys drive the served bundle, and the hub's tests check how each hub serves it. Isolation is per file, not per test: Vitest gives each file a fresh iframe and shares a worker's browser context between its files, by design. Keeping every assertion of the outside-driven tests in Browser Mode needed a clock Vitest cannot see, relying on its internals, so the tests were written for Vitest's clock instead. MSW is not used: with one router behind the hub's handler it would have only a request to pass on, which replacing `fetch` does. jsdom shows neither focus nor `inert` nor layout. Splitting the suite across more jobs with Vitest's `--shard` shortens the wait and keeps the cost. What the stand-in cannot vouch for is what the contract does not state, such as which member may do what, or the order of a list: the journeys and the hub's own tests carry that. Reconsider the alias when TanStack Start's Vitest plugin is released (TanStack/router#8965) and mounts the app as built. Reconsider the deadline tests if Vitest stops moving fake timers during actions or makes it optional (vitest-dev/vitest#11242). Reconsider running the journeys on one hub when a page depends on something the hubs do differently that no test of the API shows.

Container tests (real programs through the container backend) live in the same suite but are tagged and skipped by default, because they need Docker and an image build: the default `vp test` run excludes them, a separate run includes them, and CI runs them with the other checks when a pull request enters the merge queue.
