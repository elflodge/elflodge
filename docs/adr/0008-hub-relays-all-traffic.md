# The hub is the only address; each Runner holds a WebSocket to it

Callers and Runners connect only to the hub, and hosts are never reachable from outside. Each Runner on a host opens one WebSocket to the hub and keeps it open, reopening it when it drops; what travels on it is ADR 0026's protocol. On Workers, one Durable Object per Runner holds the socket with Cloudflare's hibernation API. Every 30 seconds the Runner sends a heartbeat, a `ping` text message that the runtime answers with `pong` without waking the object, and a Runner whose heartbeats go unanswered for three intervals starts a new connection. The hub keeps no online state, only when it last saw each Runner; every write can only move that time forward, so writes arriving late, twice or out of order cannot make it wrong. The hub stores jobs' outputs and events and serves them to callers, so polling and inspecting a running job go through one place.

A Runner registers with a registration key and receives a key of its own. It keeps its own key in its data directory and connects with it. The hub takes the Runner's identity from that key, so one Runner cannot connect as another, and a restarted Runner keeps its identity.

The Compose Runner on the hub host gets a registration key without expiry. It stays in the private `.env` beside the hub's secrets so the Runner can register again if it loses its volume. For another machine, Add Runner issues a one-day key. One day is the shortest lifetime the hub accepts and limits how long a key copied to another host can register more Runners. Sharing the Compose key with those hosts would give each of them that ability until revocation. When a host is compromised, revoke any still-valid registration key it holds as well as removing its Runner. Other registered Runners keep working with their own keys. Reconsider the Compose key's lifetime if the Runner can recover its identity after volume loss without registering again, and the one-day lifetime for other hosts if the hub accepts a shorter registration window.

Removing a Runner deletes its own key, and the database deletes the Runner's record with it. The hub answers a key it does not know with a code saying so, and a Runner stops only on that answer, as a GitHub Actions runner stops only on its server's `invalid_client`; any other refusal, from a proxy or from a hub that cannot reach its database, is retried.

We considered the opposite: the hub assigns a Runner and returns its address, and callers then talk to that Runner directly, keeping long-lived traffic off a central service. We rejected it because company hosts sit behind NAT and firewalls, so every host would have to be made reachable; every Runner would have to check identities and keep its own audit trail; a dead host would take finished outputs with it; and jobs on different hosts could not reach each other at all. A hub that everyone connects out to solves all four.

We also considered Runners polling the hub over plain HTTPS. It needs no object per connection, but idle Runners keep making requests (three Runners polling every two seconds exceed the Workers free plan's 100,000 requests a day), commands wait for the next poll, and every event batch is a full request where a socket message is billed at a twentieth of one. On a hub running on its own server the two cost about the same: an idle socket held with `ws` takes about 14 KB, and polling a request and a query per interval. GitLab and GitHub Actions use polling with server fleets billed for CPU rather than per request, and GitLab recommends long polling as the number of clients grows. The heartbeat is our own because nothing below provides one: Cloudflare closes idle WebSockets and recommends a client-side heartbeat, Workers WebSockets cannot send protocol pings, the hub's runtime answers and records only a text message without waking the hub, and partysocket neither sends heartbeats nor notices a silent peer.

## Consequences

The Runner remains the source of truth for executing a job: pi-durable's state and the workspace stay on its host, and a job carries on there, recovered after a restart or resumed after a pause. A running job is not moved to another host, since carrying it on elsewhere would need its workspace as well as pi's state. The hub keeps every event of a job and its output, forwarded as they happen, so a job can be inspected at any time, including after its host has gone away.

Every Runner dials the hub by URL, so opening a socket has a time limit, 4 seconds as partysocket's connection timeout, and it bounds only the attempt to open the socket: a limit attached to the upgrade request itself also closes the open socket when it fires. Reconnecting follows partysocket's other defaults too: the delay grows from about 3 to 10 seconds, and only a connection that stayed open for 5 seconds starts it over, so a hub that accepts and then drops Runners is not redialled at a fixed pace. Each delay varies by up to a fifth either way, as gRPC's connection backoff specifies, so Runners dropped together, as when a hub restarts, do not redial together; partysocket varies only its first delay, once per process. partysocket itself does not fit, because it reconnects underneath by itself, while oRPC's WebSocket link treats each close as the end of that connection. A Runner needs a network that lets WebSockets through to the hub. Socket.IO, SignalR and Buildkite's agent fall back to polling where proxies block WebSockets; Runners have no such fallback until a network needs one. If a heavy stream ever needs to bypass the hub, the hub can hand the client a short-lived direct address to the Runner; the client hides this, so the API does not change.
