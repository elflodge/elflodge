# A job whose Runner is silent shows its status unknown

A job sent to a Runner keeps the last status its Runner confirmed. Once the hub has heard nothing of it for seven minutes, the job also shows `statusUnknown`, with why: its Runner has not been heard from at all (`runnerDisconnected`), or has, but has not reported this job (`notReported`), as when the job's journal cannot be read. A Batch counts such jobs beside its counts by status, the job list filters by it, and `jobs wait` and `batches submit --wait` say on stderr when it appears and when it clears, and keep waiting. Each job also shows the Runner it was last sent to, whether that Runner is connected and when it was last seen, and when the job was last reported; an API key cannot read the Runner listing, so the job carries what a caller needs. Nothing moves or ends the job meanwhile: it may still be running, and its Runner carries on from where it was once it reports again.

The hub stores two times that only move forward: when it last heard from each Runner, from its hellos, syncs and reports (ADR 0026), and when each job's current run was last reported, from any report of that run the hub accepts, one behind the hub's position or partway through a backlog included. Before a run's first report, its placement stands in. Both are written at most once a minute, a third of the sync interval, so a Runner that syncs on time is never recorded as more than about one interval behind. Whether a Runner is connected and whether a job's status is unknown are worked out wherever they are read, by one rule with one threshold: nothing is written when a Runner goes silent, and nothing must clear it. Kubernetes keeps a pod's phase `Running` when its node stops reporting, sets the pod's `Ready` condition to `False` and the node's to `Unknown`; ECS keeps a task `RUNNING` and sets its instance's `agentConnected` to false. Both keep the last status and show the lost contact apart.

The threshold is the hub's existing seven minutes, two sync intervals and a minute, so a Runner that misses one pass is not flagged, and a silence the Runner heals itself, as a dropped connection it redials, never shows.

## Considered options

- A status value, as Nomad's allocation status `unknown`: a job's status only moves forward, and Batch counts, the failure breaker, the hub's report rules and the CLI's waits depend on that. A Batch whose jobs were all unknown would count as finished, the last confirmed status would be lost, and a queued job with a control waiting could not show it. Nomad's scheduler acts on its `unknown`, replacing the work after a timeout, so the status suits it; nothing here acts on silence yet.
- Recording each disconnection, as Nomad writes a node's status when its heartbeat timer expires: it needs a timer per Runner, which the Docker hub loses on restart and the Workers hub could keep only in an alarm, one more timer in an object that must hibernate (ADR 0026). An old socket's close can be handled after the new socket's hello, so the write would need fencing, and a failed write would leave a Runner connected for good. Times read against now need none of it.
- Recording each heartbeat, for a threshold of two minutes: on Workers the runtime answers a heartbeat without waking the hub, which would have to wake each Runner's object every 30 seconds to see it. The Runner sends heartbeats apart from its reports, so they can go on while reporting stalls, and they would prove less than what callers need. A heartbeat silence the Runner heals itself can also last two and a half minutes, so the threshold could not be much shorter than three.
- Asking a Runner's connection on each read: it wakes a hibernating object per read, cannot be counted or filtered in SQL, and differs between the two hubs.
- A Runner sending an explicit error for a journal it cannot read: absence covers that, a report the hub refuses, and a run the Runner keeps dropping, under one rule with no state to clear. A reason naming the cause can be added.
- Ending or moving a job whose status is unknown: whether the hub may end work without its Runner is one decision with ending a deleted job's owed deletion, and moving work is placement across hosts.

Reconsider when something must react to silence without anyone reading, such as an alert: that needs a write or a timer. For faster detection, shorten the sync interval, which the hub tells each Runner.

## Consequences

Each job read looks up its Runner's row by key, and a Batch's read and the filtered job list evaluate the rule per job. A held job still preparing, as while its Input files download, has no journal to report from, so a Runner sends a report with nothing in it for each such job in its pass over every job, or the job would show `notReported`. A job whose Runner is removed keeps its Runner's ID in the hub but shows no Runner, as the Runner's row is gone.
