# A job whose Runner is silent shows its status unknown

A job sent to a Runner keeps the last status its Runner confirmed. Once the hub has heard nothing of it for two minutes, the job also shows `statusUnknown`, with why: its Runner has not been heard from at all (`runnerDisconnected`), or has, but has not reported this job (`notReported`), as when the job's journal cannot be read. A Batch counts such jobs beside its counts by status, the job list filters by it, and `jobs wait` and `batches submit --wait` say on stderr when it appears and when it clears, and keep waiting. Each job also shows the Runner it was last sent to, whether that Runner is connected and when it was last seen, and when the job was last reported; an API key cannot read the Runner listing, so the job carries what a caller needs. Nothing moves or ends the job meanwhile: it may still be running, and its Runner carries on from where it was once it reports again.

The hub stores two times: when it last heard from each Runner, from its hellos, syncs and reports (ADR 0026), and when each job's current run was last reported, from any report of that run the hub accepts, one behind the hub's position or partway through a backlog included. A resume starts the job's time over, as it starts a new run, and before a run's first report its placement stands in. Neither is written for its own sake more than every ten seconds, the Runner's on each connection and the job's on its row, so a recorded time is never more than that older than what the hub last heard; a job's time also goes with any change its report makes. Only reports of the run that placement or a resume last named write a job's time, checked on its progress row once the report holds that row's lock, so a report of the run a resume replaced never writes it, and reports still need not lock the job's row. Whether a Runner is connected and whether a job's status is unknown are worked out wherever they are read, by one rule with one threshold: nothing is written when a Runner goes silent, and nothing must clear it. Kubernetes keeps a pod's phase `Running` when its node stops reporting, sets the pod's `Ready` condition to `False` and the node's to `Unknown`; ECS keeps a task `RUNNING` and sets its instance's `agentConnected` to false. Both keep the last status and show the lost contact apart.

The threshold is two minutes, chosen for how soon a caller deciding whether to wait, cancel or resubmit should learn that the hub has lost contact, and Runners sync every minute so that it can be that short: the pass over every held job is what keeps each job's time recent. A healthy Runner's times are at most about 77 seconds old, an interval with its jitter, a pass and its report, which took under a second with 64 idle jobs, and the ten seconds a time may go unwritten; the rest is headroom for a slow host or database. A dropped connection the Runner redials can show for a moment, which is true while it lasts. Systems that track remote workers flag after a few missed signals: Kubernetes a node after 50 seconds of 10-second lease renewals, Nomad a client after its heartbeat interval and 10 seconds, Mesos an agent after five missed 15-second pings. A job's report while it is still preparing has precedents too: GitHub Actions renews a job's lease before its worker starts, and GitLab Runner sends a quiet job's state with no new output.

## Considered options

- A status value, as Nomad's allocation status `unknown`: a job's status only moves forward, and Batch counts, the failure breaker, the hub's report rules and the CLI's waits depend on that. A Batch whose jobs were all unknown would count as finished, the last confirmed status would be lost, and a queued job with a control waiting could not show it. Nomad's scheduler acts on its `unknown`, replacing the work after a timeout, so the status suits it; nothing here acts on silence yet.
- Recording each disconnection, as Nomad writes a node's status when its heartbeat timer expires: it needs a timer per Runner, which the Docker hub loses on restart and the Workers hub could keep only in an alarm, one more timer in an object that must hibernate (ADR 0026). An old socket's close can be handled after the new socket's hello, so the write would need fencing, and a failed write would leave a Runner connected for good. Times read against now need none of it.
- Recording each heartbeat: on Workers the runtime answers a heartbeat without waking the hub, which would have to wake each Runner's object every 30 seconds to see it. The Runner sends heartbeats apart from its reports, so they can go on while reporting stalls: a job would still need its reports, under a second threshold, and a heartbeat proves less than what callers need.
- The three-minute sync and seven-minute threshold the hub had: slow detection was harmless while nothing read it but the hint to sync, but a caller now does, and a sync a minute costs each Runner's object one wake a minute.
- Asking a Runner's connection on each read: it wakes a hibernating object per read, cannot be counted or filtered in SQL, and differs between the two hubs.
- A Runner sending an explicit error for a journal it cannot read: absence covers that, a report the hub refuses, and a run the Runner keeps dropping, under one rule with no state to clear. A reason naming the cause can be added.
- Ending or moving a job whose status is unknown: whether the hub may end work without its Runner is one decision with ending a deleted job's owed deletion, and moving work is placement across hosts.

Reconsider when something must react to silence without anyone reading, such as an alert: that needs a write or a timer. Before anything acts on the marker, such as moving, ending or alerting on jobs, measure the headroom again under real load: a false marker would then cost work rather than a moment's notice. For faster detection, lower the threshold, shortening the sync interval with it to keep the headroom; the hub tells each Runner its interval.

## Consequences

Each held job's progress row is written once a minute, in its Runner's pass, and each Runner's row at most every ten seconds. Each job read looks up its Runner's row by key, and a Batch's read and the filtered job list evaluate the rule per job. A held job still preparing, as while its Input files download, has no journal to report from, so a Runner sends a report with nothing in it for each such job in its pass over every job, or the job would show `notReported`. A job whose Runner is removed keeps its Runner's ID in the hub but shows no Runner, as the Runner's row is gone.
