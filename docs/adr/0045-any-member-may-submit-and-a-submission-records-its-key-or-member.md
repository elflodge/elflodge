# Any member may submit, and a submission records its key or its member

Creating a Batch, adding jobs to it, checking Blobs (`POST /blobs/check`) and uploading them (`PUT /blobs/{digest}`) take a member's session as well as an API key holding `job:create`, as the other job calls do, so the dashboard can submit with the session its member signed in with, and send a file's bytes itself, as a key's caller does. Every member may submit: no role grants it, as every member can already pause, resume, cancel and delete any job. A member's unsafe request passes the hub's CSRF check as every other one does (ADR 0043). A Batch ID is unique within the Organization, and a job's custom ID is unique within its Batch. Either submission may be retried by another submitter. Repeating a creation with the same ID and content returns the existing Batch, even after cancellation. On an add, the hub checks the job inputs and Blob ownership first. A cancelled Batch then refuses the add with 409 before comparing content under an existing custom ID. An exact retry returns the existing job while that job exists and the Batch accepts jobs. Deleting the job frees its custom ID for a new job (ADR 0033).

A Batch, a job and a Usage record each record their submitter as the API shows it, a kind and an ID: `submitterKind`, an enum of `key` and `member`, and `submitterId`, the key's ID or the member's user ID. `submitterName` copies the submitter's name as it was then. Different callers can share a key. The key itself keeps its creator for key management. The IDs are copied rather than referenced (ADR 0020): Better Auth deletes a revoked key's row, and a user's ID is copied alike, though the hub deletes no user, as Better Auth's account deletion is off. The API shows a submitter as `{ kind, id, name }` on a Batch, whose submitter created it, and on a job, whose submitter added it, when they are read or listed. A read of usage groups by submitter and filters by one in the same terms: the filter is an object of `kind` and `id`, `submitter[kind]=member&submitter[id]=…` in the query string, so it matches the group field for field and the hub parses nothing. Kind and ID are stored as the reads and the filter use them, and together identify a submitter group, so nothing maps a kind to a column of its own, and a later kind is one more enum value rather than a column on three tables. The database no longer brands the ID by its table, as `submitterId` holds a key's or a user's; the hub brands it where it writes one, from the key or the session it verified.

## Considered options

- Letting only some roles submit: a role permission would guard little while every member can stop and delete any job, and the dashboard would need a key, or a role setting, before a plain member could submit from it.
- Keeping `submitterKeyId` for keys only, with a nullable member column beside it: reusing the former creator column for member submissions would give it two meanings. A reader would need the submission kind to interpret it.
- Two nullable ID columns, one per kind, with a CHECK keeping exactly one set: such columns pay off when each is a foreign key, which ADR 0020 rules out for these copied IDs, so a column per kind gives nothing back for the conversions between kind and column it needs, and a later kind would add a column to three tables.
- An `include` parameter for the submitter: it is three small columns of the row each read already reads, so leaving it out saves the hub nothing, while every Batch and job would come in two shapes for clients to handle.
- A single `kind:id` string as the usage filter: it would let the parameter repeat to name several submitters at once, but no page needs that, and the object needs no parsing.

## Consequences

The migration renames the submitter columns. The Docker hub applies it after the previous hub stops. On Workers the previous version can still serve after setup and fail on the old column names until the new version takes over (ADR 0047). A client that checks answers against this contract refuses a Batch from an earlier hub, which has no `submitter`. A deleted job shows no submitter, as its read keeps only its status, times and totals; its Usage records keep it. The hub validates each Submitter against a closed union. A client built for those kinds can reject a new one, so a release adding a kind marks the change as breaking.

## When to reconsider

When a client is released independently of the hub: its compatibility needs may call for an open Submitter union. When an Organization needs members who may read but not submit, such as viewers: submission then takes a role permission. When filtering usage by several submitters at once is wanted: the `kind:id` string then fits. When submitter IDs become real foreign keys, the hub joins them to their tables, or a kind's ID needs another SQL type than text: a column per kind then pays off.
