# @elflodge/pi-durable-compat

Run Pi coding-agent extensions on pi-durable.

This package isn't part of Pi. It was built for [Elflodge](https://github.com/elflodge/elflodge)'s Runner, which runs many unattended agents in one process, and it is tested with the extensions listed below. pi-durable has no built-in way to run coding-agent extensions yet (earendil-works/pi#10386). When it does, this package will point you to it.

## Usage

```sh
npm install @elflodge/pi-durable-compat @earendil-works/pi-durable @earendil-works/pi-ai @earendil-works/chord
```

Prepare the extensions once when your process starts, then attach them to each conversation before you submit to it:

```ts
import { prepareExtensions, startExtensionHost } from "@elflodge/pi-durable-compat";

const prepared = await prepareExtensions({
  sources: ["npm:pi-web-access@0.47.0"],
  dir: "/var/cache/my-app/pi-extensions",
});
const host = startExtensionHost({ prepared });

const registry = createRegistry();
const harness = await Harness.open(storage, { models, registry }, context);
const conversation = await harness.root(context, { agent: { model } });
const extensions = await host.attach(
  { harness, conversation, registry, models, env, cwd },
  context,
);

const input = await extensions.input(prompt);
if (input.action !== "handled") {
  const content = input.action === "transform" ? input.text : prompt;
  await conversation.submit({ type: "input", content }, context);
}
// When the conversation's work is done:
await extensions.close();
```

`prepareExtensions` installs the sources with Pi's own package manager, as `pi install` does (npm sources need npm), and bundles them with Rolldown into one build that keeps only the parts of Pi's packages they use. The entry of each extension installed in `dir` is written beside its source, as `<name>.pi-durable-compat.mjs`, so a package finds the files it reads relative to that entry; extensions from local paths outside `dir`, and the code extensions share, go in `dir/bundle`. The build runs in a child process, so the several hundred MiB it takes go back to the system when it ends. Pi reuses the installed packages while the sources stay the same; the build is made again on every call, in about a second, so no change to an extension or to Pi is missed. Call it once per process, with a `dir` of its own: a call builds again the bundle a running host's workers load. `failures` lists the sources that could not be installed or bundled; the rest work without them.

`startExtensionHost` runs the extensions in worker threads: none while no conversation is attached, at most `maxWorkers` (default 2), each hosting many conversations. Every conversation gets its own instance of each extension, as every Pi session does. The first `attach` through a registry installs one pi-durable extension in it, `pi-durable-compat`, with the extensions' tools and only the hooks some extension listens to; its tools and hooks act for whichever attached conversation they run in. A registry serves one Harness. Its conversations are offered each tool as the first of them to register it described it; a conversation whose own extensions did not register the tool, or hid it, fails its calls. pi-durable selects every installed extension for every conversation unless told otherwise, so a conversation you did not attach, such as a subagent's, is offered the tools too and its calls to them fail; attach it, or leave the extension out of its selection with pi-durable's `extensions` setting.

## What extensions get

| Pi API                                                                                                                                                                                                                                                                            | Here                                                                                                                                                                                                                                                                                                                                                                                                            |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `registerTool`, including `prepareArguments`, `executionMode`, `exposure` and `defaultActive`                                                                                                                                                                                     | Registered with pi-durable; calls run in the worker and are cancelled with the call. Tools Pi does not activate when they are registered are deferred.                                                                                                                                                                                                                                                          |
| `on("tool_call")`, `on("tool_result")` | Run for every tool call, the host's own tools included: block a call, change its arguments or its result. |
| `on("tool_execution_start")`, `on("tool_execution_end")` | Observed for every tool call, the host's own tools included; what handlers return is ignored. |
| `on("context")`, `on("context_with_system")`, `on("before_provider_request")`                                                                                                                                                                                                     | Change a request's messages or its provider payload.                                                                                                                                                                                                                                                                                                                                                            |
| `on("before_agent_start")`, `on("agent_start")` | Once per run, at its first request. What handlers add to `systemPromptOptions` (`sections`, `appendSystemPrompt`, `promptGuidelines`) is added to each of the run's requests, except those a host that restarted during the run sends after its first; a message they return goes with the first request and is saved to the conversation after its answer; a changed `selectedTools` applies from the next request. A returned `systemPrompt` is ignored: pi-durable builds the prompt, and `event.systemPrompt` and `ctx.getSystemPrompt()` show the prompt Pi would build from the options. |
| `on("turn_start")`, `on("message_end")`, `on("turn_end")`, `on("agent_end")` | Observed; what handlers return is ignored. `message_end` is for the model's messages only, those of failed attempts included; a final answer's `turn_end` comes before it is saved, so it has no entry ID; `agent_end` follows only runs that answered. |
| `on("session_before_compact")`                                                                                                                                                                                                                                                    | `cancel` declines the compaction and `compaction.summary` replaces pi-durable's summary; the rest of the result is ignored. `preparation` carries the messages to summarize and the first kept entry's ID.                                                                                                                                                                                                      |
| `on("input")`                                                                                                                                                                                                                                                                     | Run by `extensions.input()` on input before you submit it.                                                                                                                                                                                                                                                                                                                                                      |
| `on("session_start")`, `on("session_shutdown")`                                                                                                                                                                                                                                   | On `attach`, with reason `resume` if the conversation has entries already, and on `close`, which keeps what the handlers write.                                                                                                                                                                                                                                                                                 |
| `appendEntry`, `ctx.sessionManager.getBranch()`, `getEntries()`, `getEntry()`, `getLeafId()`                                                                                                                                                                                      | Saved in the conversation's journal and read back from it, also right after a write.                                                                                                                                                                                                                                                                                                                            |
| `sendMessage`, `sendUserMessage`, `ctx.compact()`, `ctx.abort()`                                                                                                                                                                                                                  | Submitted to the conversation. Dropped after `close`.                                                                                                                                                                                                                                                                                                                                                           |
| `exec`                                                                                                                                                                                                                                                                            | Runs in the `env` given to `attach`, with Pi's options: `cwd` (default `ctx.cwd`), `timeout`, `signal` and `maxBuffer`.                                                                                                                                                                                                                                                                                         |
| `ctx.model`, `ctx.isIdle()`, `setModel`, `getThinkingLevel`, `setThinkingLevel`, `getActiveTools`, `setActiveTools`, `getAllTools`, `ctx.modelRegistry` (`find`, `getAll`, `getAvailable`, `hasConfiguredAuth`, `getApiKeyAndHeaders`, `getProviderAuth`, `getApiKeyForProvider`) | Read from and made to the conversation's agent and the `models` given to `attach`; `setActiveTools` offers the model exactly those tools from the next request, `setModel` switches only to a model with credentials, and `model_select` and `thinking_level_select` follow a switch, as in Pi.                                                                                                                 |
| `events`, `registerFlag`, `getFlag`                                                                                                                                                                                                                                               | As in Pi, shared by one conversation's extensions.                                                                                                                                                                                                                                                                                                                                                              |
| Tools and handlers registered after loading                                                                                                                                                                                                                                       | The conversation's pi-durable extension is installed again with them.                                                                                                                                                                                                                                                                                                                                           |
| `registerProvider`, `registerVirtualModel`                                                                                                                                                                                                                                        | Not supported: the host makes model calls with the `models` given to `attach`. While loading, reported in `errors`, and the extension keeps the rest; later, they throw.                                                                                                                                                                                                                                        |
| Commands, shortcuts, renderers, UI                                                                                                                                                                                                                                                | Accepted and unused, as in Pi's print mode: `ctx.hasUI` is false.                                                                                                                                                                                                                                                                                                                                               |

Outside `before_agent_start` handlers, `ctx.getSystemPrompt()` returns an empty prompt, and `ctx.getContextUsage()` nothing: pi-durable builds the prompt for each request and does not expose it. Handlers for Pi's other events, such as `agent_settled`, `session_compact`, `session_tree` and `message_update`, are accepted and never run. Every other Pi API either does nothing here or throws an error saying it is not supported.

## Tested extensions

- [`pi-web-access`](https://www.npmjs.com/package/pi-web-access) 0.47.0: loads and registers its tools; `fetch_content` fetches pages and reads PDFs.
- [`pi-web-search`](https://www.npmjs.com/package/pi-web-search) 1.7.0: loads and registers its tools.

Other extensions work as far as they use what the table above lists; only these are tested.

## Limits

- Extensions run in worker threads of your process with its permissions. A worker thread is not a sandbox: `exec` goes through your `env`, but an extension that uses `node:fs` or `node:child_process` itself is not contained. Install only extensions you trust.
- Extensions' modules load once per worker and are shared by its conversations. State an extension keeps in its factory is per conversation; state at module level is per worker.
- An extension that does not bundle is not loaded; loading it as Pi does would need Pi's TypeScript loader and its whole coding agent in every worker.
- Bundled code reads files relative to the file it is bundled into, through `__dirname` or `import.meta`: code in an entry finds only files relative to the entry's directory, and code in `dir/bundle` finds none. Photon, Pi's image library, stays where it is installed for this reason.
- Native add-ons load from where they are installed, and the host also loads each one in its main thread before starting workers, so a worker that exits cannot unload one that crashes when unloaded (zhangyuang/node-ffi-rs#145).
- An extension that runs work in a Pi process of its own, as `pi-subagents` does for its subagents, starts the Pi CLI there, outside pi-durable and the conversation; such extensions are not supported.
- pi-durable validates a tool's arguments on the host before the call reaches the worker, where the tool's own `prepareArguments` runs. The host first parses arrays and objects sent as JSON text, the repair models most often need; a `prepareArguments` that renames fields or fills in required ones never gets arguments that fail validation.
- When a worker exits, its conversations' extension tools fail from then on.
- A tool's `promptSnippet` and `promptGuidelines` are not added to the system prompt.
- Tool calls are recorded as unsafe to replay: after a crash, pi-durable does not run an interrupted extension tool again.
