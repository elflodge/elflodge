# @elflodge/pi-durable-compat

Run Pi coding-agent extensions on pi-durable.

This package isn't part of Pi. It was built for [Elflodge](https://github.com/elflodge/elflodge)'s Runner, which runs many unattended agents in one process, and it is tested with the extensions listed below. pi-durable has no built-in way to run coding-agent extensions yet (earendil-works/pi#10386). When it does, this package will point you to it.

## Usage

```sh
npm install @elflodge/pi-durable-compat @earendil-works/pi-durable @earendil-works/pi-ai @earendil-works/chord
```

Prepare the extensions once when your process starts, then attach them to each conversation before you submit to it:

```ts
import { prepareExtensions, startExtensionHost } from "@elflodge/pi-durable-compat";

const prepared = await prepareExtensions({
  sources: ["npm:pi-web-access@0.47.0"],
  dir: "/var/cache/my-app/pi-extensions",
});
const host = startExtensionHost({ prepared });

const registry = createRegistry();
const harness = await Harness.open(storage, { models, registry }, context);
const conversation = await harness.root(context, { agent: { model } });
const extensions = await host.attach(
  { harness, conversation, registry, models, env, cwd },
  context,
);

const input = await extensions.input(prompt);
if (input.action !== "handled") {
  const content = input.action === "transform" ? input.text : prompt;
  await conversation.submit({ type: "input", content }, context);
}
// When the conversation's work is done:
await extensions.close();
```

`prepareExtensions` installs the sources with Pi's own package manager, as `pi install` does (npm sources need npm, or the command given as `npmCommand`), and bundles them with Rolldown into one build that keeps only the parts of Pi's packages they use. The entry of each extension installed in `dir` is written beside its source, as `<name>.pi-durable-compat.mjs`, so a package finds the files it reads relative to that entry; extensions from local paths outside `dir`, and the code extensions share, go in `dir/bundle`. The build runs in a child process, so the several hundred MiB it takes go back to the system when it ends; its output, the package manager's included, goes to standard error, as Pi sends it when its standard output carries a protocol. An aborted `signal` ends the child process and rejects with Node's `AbortError`. Pi reuses the installed packages while the sources stay the same; the build is made again on every call, in about a second, so no change to an extension or to Pi is missed. Call it once per process, with a `dir` of its own: a call builds again the bundle a running host's workers load. `failures` lists the sources that could not be installed or bundled; the rest work without them.

`startExtensionHost` runs the extensions in worker threads: none while no conversation is attached, at most `maxWorkers` (default 2), each hosting many conversations. Every conversation gets its own instance of each extension, as every Pi session does. A handler that fails after its extension loaded is reported to `onError`, with the extension, the event and the error's message and stack as Pi's runner reports them, by default on standard error, as Pi's print mode does, and the conversation goes on. `workerOptions` passes Node's `resourceLimits` and `env` to the workers: a memory limit makes a worker that runs out exit alone. Closing a conversation's extensions waits up to `closeTimeout` (default 10 s) for their `session_shutdown` handlers. The first `attach` through a registry installs one pi-durable extension in it, `pi-durable-compat`, with the extensions' tools and only the hooks some extension listens to; its tools and hooks act for whichever attached conversation they run in. A registry serves one Harness and one host. Its conversations are offered each tool as the first of them to register it described it; a conversation whose own extensions did not register the tool, or hid it, fails its calls. pi-durable selects every installed extension for every conversation unless told otherwise, so a conversation you did not attach, such as a subagent's, is offered the tools too and its calls to them fail; attach it, or leave the extension out of its selection with pi-durable's `extensions` setting, as in `configure({ extensions: { remove: [{ name: "pi-durable-compat" }] } })`. Flags that change which tools an extension registers need a registry for each group of conversations that share them.

Outside `before_agent_start` handlers, `ctx.getSystemPrompt()` returns an empty prompt, and `ctx.getContextUsage()` nothing: pi-durable builds the prompt for each request and does not expose it. Handlers for Pi's other events, such as `agent_settled`, `session_compact`, `session_tree` and `message_update`, are accepted and never run. Every other Pi API either does nothing here or throws an error saying it is not supported.

## Tested extensions

- [`pi-web-access`](https://www.npmjs.com/package/pi-web-access) 0.47.0: loads and registers its tools; `fetch_content` fetches pages and reads PDFs.
- [`pi-web-search`](https://www.npmjs.com/package/pi-web-search) 1.7.0: loads and registers its tools.

Other extensions work as far as they use what the table above lists; only these are tested.

## Limits

- Extensions run in worker threads of your process with its permissions. A worker thread is not a sandbox: `exec` goes through your `env`, but an extension that uses `node:fs` or `node:child_process` itself is not contained. Install only extensions you trust.
- Extensions' modules load once per worker and are shared by its conversations. State an extension keeps in its factory is per conversation; state at module level is per worker.
- An extension that does not bundle is not loaded; loading it as Pi does would need Pi's TypeScript loader and its whole coding agent in every worker.
- Bundled code reads files relative to the file it is bundled into, through `__dirname` or `import.meta`: code in an entry finds only files relative to the entry's directory, and code in `dir/bundle` finds none. Photon, Pi's image library, stays where it is installed for this reason.
- Native add-ons load from where they are installed, and the host also loads each one in its main thread before starting workers, so a worker that exits cannot unload one that crashes when unloaded (zhangyuang/node-ffi-rs#145).
- An extension that runs work in a Pi process of its own, as `pi-subagents` does for its subagents, starts the Pi CLI there, outside pi-durable and the conversation; such extensions are not supported.
- pi-durable validates a tool's arguments on the host before the call reaches the worker, where the tool's own `prepareArguments` runs. The host first parses arrays and objects sent as JSON text, the repair models most often need; a `prepareArguments` that renames fields or fills in required ones never gets arguments that fail validation.
- When a worker exits, the tool calls running in it fail with the reason, such as running out of memory, and its conversations' extensions are opened again on another worker, with `session_start` reason `resume`, as after a restart: what they kept in memory is lost, and the other conversations on that worker restart with them. A conversation whose extensions fail to open again, as when the new worker also exits or loading takes longer than `closeTimeout`, stays without them, as does every one with `restart: false`: its extension tools fail, its hooks no longer run, and if its extensions handle `tool_call`, its tool calls are blocked, as Pi blocks a call when a `tool_call` handler fails. `onWorkerExit` gets which conversations were opened again and which were lost, by default on standard error.
- Tool calls are recorded as unsafe to replay: after a crash, pi-durable does not run an interrupted extension tool again.
