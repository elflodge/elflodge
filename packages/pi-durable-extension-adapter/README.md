# @elflodge/pi-durable-extension-adapter

Use Pi's coding-agent extensions in apps built on pi-durable.

[Pi](https://www.npmjs.com/package/@earendil-works/pi-coding-agent) has a large collection of third-party extensions: npm packages that give the agent tools such as web search, react to its events and keep state in its session. [pi-durable](https://www.npmjs.com/package/@earendil-works/pi-durable), Pi's library for agents whose conversations survive a restart, has an extension format of its own and cannot load them ([earendil-works/pi#10386](https://github.com/earendil-works/pi/issues/10386)). An app built on pi-durable therefore starts without the tools Pi users already have.

This package loads those extensions, unchanged, into pi-durable conversations. You name them as you would for `pi install`, attach them to a conversation, and the model can call their tools while their handlers see the conversation's events.

It was built for [Elflodge](https://elflodge.com), which runs hundreds of Pi agents unattended and in parallel on your own machine, each returning results checked against your schema. You don't need Elflodge to use it: it works in any app built on pi-durable. There is [more about Elflodge](#elflodge) at the end.

## What you get

- Extensions install from the same sources as `pi install` takes: an npm package, a git repository or a local path. Pi's own package manager installs them.
- Extensions run on Pi's own code. Pi's loader and runner load them and call their handlers, so the order of handlers, the way their results combine and the way one failing handler is kept from the others are Pi's. Where pi-durable works differently from Pi's coding agent, the [table below](#what-extensions-get) says what an extension sees.
- What extensions save is as durable as the conversation. Entries from `appendEntry` and the messages extensions send are written to the conversation's journal, so an extension finds its state again after a restart.
- Many conversations share a few worker threads. Each conversation gets its own instance of every extension, as each Pi session does, while the extensions' code loads once per worker, bundled with only the parts of Pi it uses. Two workers with 50 conversations attached, each with `pi-web-access` and `pi-web-search`, added 74 MiB to the process.
- Your app stays responsive. Extensions run in worker threads, so an extension's heavy synchronous work, such as parsing a large page, does not stall pi-durable or your own code.
- Your app survives an extension that crashes. An uncaught error, `process.exit()` or a full heap ends only the worker it happened in, and the conversations on that worker get their extensions back on another one.
- An extension that hangs while it opens or closes cannot stall a conversation's start or end: each has a time limit of 10 s.

The extensions tested so far are listed under [Tested extensions](#tested-extensions). Where Pi's extension API has no counterpart in pi-durable, or a kind of extension is not supported, the [table of Pi APIs](#what-extensions-get) and the [limits](#limits) say so.

## Quick start

Add it to an app set up as [pi-durable's README](https://www.npmjs.com/package/@earendil-works/pi-durable) shows, on Node 22.19 or later:

```sh
npm install @elflodge/pi-durable-extension-adapter
```

It uses your app's Pi 1.x packages, version 1.6.0 or later. Extensions from npm sources also need `npm` on the machine.

Prepare the extensions once when your process starts, then attach them to each conversation before you submit to it:

```ts
import { createRegistry, Harness } from "@earendil-works/pi-durable";
import { prepareExtensions, startExtensionHost } from "@elflodge/pi-durable-extension-adapter";

// Once, when the process starts.
const prepared = await prepareExtensions({
  sources: ["npm:pi-web-access@0.47.0"],
  dir: "/var/cache/my-app/pi-extensions",
});
for (const { source, message } of prepared.failures) console.error(`${source}: ${message}`);
const host = startExtensionHost({ prepared });

// Your pi-durable setup, with the registry kept in a variable.
const registry = createRegistry();
const harness = await Harness.open(
  storage,
  // The extensions every conversation selects, yours if any; `attach` adds each conversation's own.
  { models, registry, settings: { extensions: [] } },
  context,
);
const conversation = await harness.root(context, { agent: { model } });

// For each conversation, before you submit to it.
const extensions = await host.attach(
  { harness, conversation, registry, models, env, cwd },
  context,
);

// Extensions see a prompt before the model does, as in Pi.
const input = await extensions.input(prompt);
if (input.action !== "handled") {
  const content = input.action === "transform" ? input.text : prompt;
  const submission = await conversation.submit({ type: "input", content }, context);
  await submission.wait(context);
}

await extensions.close(); // when the conversation's work is done
await host.close(); // when the process shuts down
```

`storage`, `models`, `model` and `context` are what you already pass to pi-durable. `env` is a pi-durable `ExecutionEnv`, such as `NodeExecutionEnv`, in which `pi.exec` runs commands; without one, `pi.exec` throws.

Check what did not load. `prepared.failures` lists the sources that could not be installed or bundled or have no extension, and `extensions.errors` lists the extensions that failed to load for this conversation, and the provider registrations the adapter refused, whose extensions otherwise run; in both cases the others work without them.

`extensions.input()` runs the extensions' `input` handlers, which can leave the prompt as it is (`continue`), replace its text and images (`transform`), or answer it themselves (`handled`), in which case you submit nothing.

An attached conversation keeps your process alive until you close its extensions or the host. `host.close()` closes the extensions of every attached conversation and stops the workers.

After a restart, attach again to the conversations you reopen. Their extensions then start with `session_start` reason `resume` and read the entries they saved before.

## Using it

### Preparing extensions

Pin the versions of npm sources. An unpinned source installs whatever version is latest at the time.

Give `dir` a directory that is kept between starts and used by one process at a time. Pi reuses the packages installed there while the sources stay the same. The entry of each extension installed in `dir` is written beside its source, as `<name>.pi-durable-extension-adapter.mjs`; everything else that is built goes in `dir/bundle`.

Call `prepareExtensions` once per process. It builds the bundle again on every call, which takes about a second, so a second call would rebuild the bundle that a running host's workers load. It runs in a child process, which takes several hundred MiB for a few extensions and gives them back when it exits.

The packages Pi supplies to extensions (`pi-ai`, `pi-agent-core`, `pi-coding-agent`, `pi-tui` and TypeBox) come from this package's own copy of the coding agent, so every extension runs on the Pi version this package was tested with. That copy is pinned to that exact version, so each Pi release reaches extensions through a release of this package. If the copy installed is another, through an override, and lacks a file the build relies on, preparing fails and names the file.

### Model providers

An extension can add models to the catalog your app already uses, or change a provider's settings, such as its base URL. To enable this, give `Harness.open` and `host.attach` the same Pi coding-agent `ModelRuntime`. With another pi-durable `Models`, such as `builtinModels`, extension tools and events work as before, and `registerProvider` and `unregisterProvider` throw, saying they need a `ModelRuntime`: an extension that registers a provider while it loads finds the error in `extensions.errors` and keeps the rest. When the conversation's extensions open again after a worker exit, or when an extension registers in a handler, the error is passed to `onError`.

A provider can use a built-in model API or supply its own `streamSimple` function. Pi composes the provider's settings in your app, where built-in APIs also make their requests. A custom stream runs in the worker, in the instance of the extension that registered it, so it can keep a query open across the tool calls of its conversation, and each conversation's requests reach its own instance. Cancelling a run cancels the request its stream is serving, and a query the stream keeps open while a tool runs, even when that tool ignores the cancellation.

`ctx.modelRegistry.getProvider(name)` lets an extension check whether the provider is available and read its ID, name and base URL. It shows a custom stream only to the conversation whose extensions registered it, so an extension that registers its provider when it finds none does so in every conversation, and again after its worker exits. Guard such a registration with `getProvider`: `find` and `getAll` list the models of a provider another conversation registered with its own stream, so an extension guarded by them skips registering, and its requests to the provider fail with "No attached conversation … has a stream registered". A guard that finds the provider registered with settings alone by another conversation's extensions skips registering too, also after its worker exits: that conversation's requests go to the other's settings, and once the last conversation that registered it closes, the provider is gone for it, or is your app's again, also when both run the same extension. So an extension that registers settings alone should register them unconditionally.

Conversations using the same `ModelRuntime` share provider settings. If an extension changes a provider's URL or credentials, another conversation's next request can send its prompt to the new server or use the new credentials. A registration with a `models` list replaces the provider's list for every conversation, as Pi defines it. That includes the startup list an extension registers when it opens again after a worker exit, or in a conversation attached later, after another conversation registered a longer list: a conversation that selected a model the list no longer has ends its next run with `no_model`. For conversations that need independent settings or model lists, use separate Harnesses, each opened with a `ModelRuntime` of its own and attached with it.

Configure the app's providers before attaching extensions. An extension that registers a provider your app already has, built-in or configured, replaces it for every conversation until the last attachment that registered it closes, and then your app's registration is back. A provider your app registered with `registerNativeProvider` is refused, since Pi would drop its models. If your app registers the provider again while extensions have it, their later registrations under that name throw, and when they close the adapter leaves the provider as it then is. To take a provider back, your app unregisters it first and then registers it in full: a partial registration merges into the extensions' one, custom stream included.

A conversation whose own extensions did not register a provider served by custom streams fails its requests to that provider's models of the streams' API with "No attached conversation … has a stream registered", so give an extension's provider a name of its own; its models of another API go to Pi's stream for that API, as in Pi. Registering a custom stream for a provider that another conversation's extensions registered with settings alone throws, unless an extension's custom stream already serves it, the conversation's own included. In the other order, the settings-only conversation's requests fail with that message until the last conversation with a stream closes; your app's own stream for that API, if it registered one, else Pi's built-in stream, then serves it with the settings merged so far, including the last stream's API and models; when only that stream implemented the API, requests fail with "No API provider registered" until a conversation registers an API Pi has, for the models too where they name their own.

A custom stream receives the request's `onPayload` hook, through which pi-durable runs `beforeProviderRequest` hooks, and the `onResponse` and `onProviderStreamEvent` hooks of an app that calls the runtime itself. Such an app passes the conversation's provider session ID as `sessionId`, read with `harness.snapshot(ProviderDoc, conversationId, context)`, which routes the request to that conversation's stream. It runs the tools a response asks for itself, so for a request it makes while the conversation has no run, a query the stream keeps open for them ends when the app aborts the signal it passed. Until then, or until the attachment closes or its worker exits, the adapter keeps its listener on that signal and the worker keeps the query's controller; a request made without a signal stays open until the close or the exit, so an app that makes many such requests over a long attachment passes a signal and aborts it once the exchange, with all its tool rounds, is done. A close ends such queries, and withdraws the conversation's providers, before the extensions' `session_shutdown` handlers run. A request it makes during a run is released with that run instead, unless the run has already answered and runs only its `afterRun` tasks; then it is kept as when the conversation has no run. A host-supplied `fetch` function cannot run in the worker. The host's telemetry object also stays in the host.

### Errors and time limits

A handler that throws does not end the conversation, as in Pi. The error is passed to `onError` with the extension, the event and the error's message and stack.

Opening and closing have time limits of 10 s. `attach` waits for the extensions to load and for their `session_start` handlers; past the limit it fails. `close` first waits for the end of a run that answered to reach the extensions, with a limit of 10 s, then for the loading and the `session_compact` and `session_compact_failed` handlers under way and for the `session_shutdown` handlers, which share another limit of 10 s; past a limit it goes on, and what the handlers do later is dropped. Tool calls and other handlers have no time limit.

`close` waits for a run's end because `submission.wait()` resolves at the answer, before the run's `agent_end` and `agent_settled` reach the extensions; closing right after it would otherwise end the session before the run. It does not wait for a run still under way, which goes on without the extensions after their `session_shutdown`, where Pi aborts it first; nor for input you queued, or for child conversations. To let those finish, await `conversation.waitForIdle(context)` before `close`; to end a run first, as Pi does, abort it with `conversation.abort(context)` and then wait.

### When a worker exits

A worker exits when an extension throws an uncaught error, calls `process.exit()` or runs past the worker's heap limit. The tool calls and model requests running in it fail with the reason. The host then opens the extensions of that worker's conversations again on another worker, with `session_start` reason `resume`, as after a restart. What they kept in memory is lost, and the other conversations on that worker restart with them. The providers they registered go at the exit, as at close, and the reopened extensions register theirs again, as at attach. A model request in flight fails with the worker's exit reason, and pi-durable's retry policy applies as to any model error: without a retry, the run ends unanswered with reason `model_error`, and a retry is a request like the next ones. Until the reopened extensions have registered, the conversation has none of their models: a run that needs one ends unanswered, with reason `no_model`, or with `model_error` when other conversations still serve the provider with streams of their own. When the exiting conversation was the last one with a registration under a provider your app has, the change its extension made, such as a base URL, goes at the exit too, so until the extension registers again, requests can go to your app's endpoint or carry your app's credentials and headers. An app whose requests must not reach its own endpoint makes the gateway its own registration, or gives that provider no credentials. While another conversation keeps a registration under that provider, even one of headers alone, the shared settings stay as merged, the exited extension's endpoint and credentials included. The next prompt after the reopening works, unless the conversation's extension had the last stream for a provider under which another conversation kept a registration of settings alone: then the reopened stream is refused, as when a settings-only conversation was there first, until that conversation closes. A provider an extension registers from a handler, rather than while it loads or in `session_start`, is back once that handler runs again.

A conversation is lost when its extensions fail to open again, or when `restart` is false. It goes on without its extensions: their tools fail, their handlers no longer run, and their providers go as at close. If its extensions handle `tool_call`, all its tool calls are blocked, as Pi blocks a call when a `tool_call` handler fails, because the host cannot tell a handler that guards calls from one that only observes them.

To act on a lost conversation yourself, for instance to fail the job, pass `onLost` to `attach`: it is called with the worker's error when that attachment's extensions are lost. `onWorkerExit` on the host receives the error and the IDs of the conversations that were opened again and of those that were lost; IDs are unique only within one Harness, so with several Harnesses on one host, as one per job, `onLost` tells their conversations apart.

### Registries and subagents

`attach` installs a pi-durable extension for the conversation, `pi-durable-extension-adapter:<conversation ID>`, with its extensions' tools and only the hooks they listen to, and adds it to the conversation's `extensions` selection; `close` uninstalls it. So each conversation is offered only its own extensions' tools, as a Pi session is, even when they differ, such as an MCP server's.

Set the Harness's `settings.extensions` to the extensions conversations select by default, as the example above does. Without it, pi-durable selects every installed extension, so every conversation would get every attached conversation's, and `attach` fails when it finds the default selection selecting one.

A registry serves one Harness and one host, and a conversation can be attached once at a time. `attach` throws otherwise.

A conversation created from an attached one, such as a subagent's or a fork, starts with its selection, so it is offered those tools and its calls to them fail. Its requests to a provider its creator's extensions serve with a custom stream fail too, since a fork gets a provider session of its own. Either attach it, which replaces the inherited extension with its own, or give it the default selection back and, when its model is one those extensions serve, a model of your app's, here for a conversation `child` that is not attached:

```ts
await child.configure({ extensions: null, model }, context);
```

## Options

### `prepareExtensions(options)`

| Option       | Default   | Meaning                                                                                                                                                                  |
| ------------ | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `sources`    | required  | The extension packages, as Pi's settings name them: `npm:pi-web-access@0.47.0`, a git URL or a local path.                                                               |
| `dir`        | required  | Where Pi installs the packages and the bundle is built. Kept between starts, for one process at a time.                                                                  |
| `npmCommand` | `["npm"]` | Pi's `npmCommand` setting: the command that runs npm, with its arguments.                                                                                                |
| `signal`     | none      | Aborting it ends the child process and rejects with Node's `AbortError`, the signal's reason as its `cause`. A package manager that has already started runs to its end. |

### `startExtensionHost(options)`

| Option          | Default        | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| --------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prepared`      | required       | What `prepareExtensions` returned.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `maxWorkers`    | `2`            | The most worker threads extensions run in. A worker busy with a handler's synchronous work holds up the conversations on it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `idleTimeout`   | `30000`        | How long a worker with no conversation stays before it exits, in milliseconds.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `onError`       | standard error | Called with a handler's error and the conversation's ID when a handler fails after its extension loaded, a registration fails when its extensions open again, or releasing a session's resources at `close` fails (event `cleanup_session_resources`). Failures of the adapter's own come with the source `<runtime>`, such as a value in a `session_before_compact` handler's `details` or `usage` that JSON cannot hold, or a failure to save them (event `session_before_compact`), or to read the session for `session_compact`; the compaction and the event go on without it. If it throws or rejects, both errors go to standard error. |
| `workerOptions` | none           | Node's `resourceLimits` and `env` for the workers. `resourceLimits` caps a worker's JavaScript heap, not memory outside it, such as buffers. `env` is their `process.env`, by default the process's.                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `restart`       | `true`         | Whether the extensions of an exited worker's conversations are opened again on another worker.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `onWorkerExit`  | standard error | Called when a worker exits with conversations attached, with the error and the conversations `reopened` and `lost`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |

### `host.attach(options, context)`

| Option         | Default  | Meaning                                                                                                          |
| -------------- | -------- | ---------------------------------------------------------------------------------------------------------------- |
| `harness`      | required | The Harness the conversation belongs to.                                                                         |
| `conversation` | required | The conversation the extensions act for.                                                                         |
| `registry`     | required | The registry the Harness was opened with.                                                                        |
| `models`       | required | The models the Harness was opened with. Extensions read them, switch between them and get credentials from them. |
| `cwd`          | required | The directory extensions see as `ctx.cwd`.                                                                       |
| `env`          | none     | The environment `pi.exec` runs commands in. Without one, `pi.exec` throws.                                       |
| `flags`        | none     | Values for the flags extensions register with `pi.registerFlag`, by name.                                        |
| `onLost`       | none     | Called with the worker's error when these extensions are lost after their worker exits.                          |

It resolves to the conversation's extensions: `errors`, `input(text, options)` and `close()`. The options of `input` are the prompt's `images`, its `source` (default `rpc`, as Pi's RPC mode reports a client's prompt) and its `streamingBehavior`, as Pi's `prompt` takes them.

Outside `before_agent_start` handlers, `ctx.getSystemPrompt()` returns an empty prompt, because pi-durable builds the prompt for each request and does not expose it. Handlers for Pi's other events, such as `session_tree` and `message_update`, are accepted and never run. Session names, labels and `ctx.shutdown()` do nothing. Every other Pi API either does nothing here or throws an error saying it is not supported.

### Runs

pi-durable has no hook where a run starts, so `before_agent_start` and `agent_start` run once per run, at its first request. They get the first input that started the run as the prompt, or as a custom message when an extension sent it with `triggerTurn`. They do not run again when the run continues after an answer or a failure. A follow-up placed after a run's answer starts a run of its own, where Pi keeps it in the same run.

What `before_agent_start` handlers add to `systemPromptOptions` (`sections`, `appendSystemPrompt`, `promptGuidelines`) is added to each of the run's requests, also after a restart in the middle of the run. A message they return goes with the first request and is saved to the conversation after its answer. A changed `selectedTools` applies from the next request. A returned `systemPrompt` is ignored, because pi-durable builds the prompt; `event.systemPrompt` and `ctx.getSystemPrompt()` show the prompt Pi would build from the options. A section whose name Pi rejects is reported to `onError` and left out, where Pi fails the run.

`message_end` is for the model's messages only. Each response has a turn, a failed attempt's included, and one that calls no tool ends its turn before it is saved, so its `turn_end` has no entry ID. A retry stays in the run, where Pi ends the run and starts it again (`agent_end`, `agent_start`). `agent_end` follows only runs that answered, and `agent_settled`, with `aborted: false`, right after it, while the conversation is still busy: there `ctx.isIdle()` is false, and input queued during the run starts the next run after it, where Pi sends `agent_settled` once nothing more will run.

## Limits

- Extensions can do anything your process can, as in Pi: they run in its worker threads with its permissions. Only `pi.exec` goes through the `env` you give `attach`, so a sandboxed `env` does not contain an extension that reads files or starts programs itself. Install only extensions you trust.
- An extension's module-level state is shared by the conversations on its worker, where in Pi one session has the process to itself. State kept in its factory is per conversation.
- A crash inside a native add-on ends your whole process; worker threads share it.
- `billion-context` does not work when it routes model requests by patching `fetch`, nor do other extensions that do so: a patch in a worker sees only that worker's requests, and built-in model APIs make theirs in your app. Its routing through a provider's base URL with `registerProvider` needs a `ModelRuntime`, as [Model providers](#model-providers) says, and is not tested.
- Extensions that run work in Pi processes of their own, as `pi-subagents` does for its subagents, are not supported.
- After a crash of your process, pi-durable does not run an interrupted extension tool again.

## Elflodge

This package comes from [Elflodge](https://elflodge.com), an open-source project for running hundreds of agents unattended behind one job API. It runs sandboxed agents in parallel on your own machine, without a costly fleet of hosted sandboxes: you send a task or a whole batch and get structured results your code can use.

You define the agent's instructions and output schema once. Each job runs Pi with real files and shell commands in its own sandbox and returns JSON checked against your schema, or a failure with its reason. The first five jobs run before the rest, and a Batch pauses itself when too many fail.

Given a folder of invoices and a JSON Schema for what you want from each, one command runs them all:

```sh
npx elflodge batches submit \
  --id invoices \
  --each invoices/*.pdf \
  --instructions "Extract the supplier, number, currency and total." \
  --output-schema invoice.schema.json \
  --wait \
  --output-dir ./results
```

Elflodge's Runner hosts many such jobs in one process, and this package was built so that their agents can use Pi's extensions there. The website is [elflodge.com](https://elflodge.com) and the source, this package's included, is at [elflodge/elflodge](https://github.com/elflodge/elflodge).

This package is not part of Pi. When pi-durable can run coding-agent extensions itself, this README will point you to it.
